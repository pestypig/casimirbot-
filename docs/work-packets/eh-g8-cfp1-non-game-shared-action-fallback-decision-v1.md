## Selected A development contract for review, not an admitted implementation

The reference canvas would be an owner-owned program document within the installed harness, with a code-owned connector profile and native document revision distinct from hosted room state. It may be packaged within the planned signed EXE, but the exact artifact and file set must be selected and verified; the inspected source has no such program. Its program authority must remain separate even if host service and canvas share one installed binary. The room stores membership, grants and attributable receipts, not an unrestricted copy of the owner's writable document. No external map, image, font or music is needed for the proposed blank canvas and CSS marker; if implementation adds such material, C03/C14 rights review expands accordingly. Before D12, map any new canvas service/code to C01, client assets to C03, any published connector surface to C10 and release bytes to C15 in the [component matrix](eh-g8-cfp1-first-customer-component-decision-sheet-v1.md); add a distinct component row if those boundaries do not cover the actual artifact. The current C01–C15 baseline cannot silently absorb future files.

Candidate operation ID: `com.casimirbot.reference_canvas.marker.place.v1` (**proposed**, absent from current registry). A host opens one named local canvas and selects an exact normalized coordinate, fixed `blue` marker style, document ID/revision, one requester account and a one-use, short-lived grant. The guest may request that one effect through the proposed [first-party ingress](eh-g8-cfp1-hosted-guest-request-ingress-v1.md) or a separately qualified MCP path; both converge on one admission and native-effect path. No caller-selected filesystem path, arbitrary script, upload, room-wide write scope or hidden background effect is allowed. The native program atomically adds at most one marker with a stable effect ID; it returns a changed document revision and marker ID. A fresh owner-side read verifies that exact marker exists at the granted coordinate. The hosted trial counts the effect **once only after verified native completion**, against its provisional ten-effect sponsor ceiling; a denied, failed or duplicate request does not consume a successful-effect unit. The same owner's separately authorized personal marker action, if offered, remains free without hosted eligibility.

Separate verified identities remain mandatory: current sponsor and room epoch; distinct host and guest accounts; program/document owner and local node; permitted guest requester; canvas connector manifest and epoch; exact document revision, coordinate, capability and grant nonce. Payment, invitation, media consent and read access do not issue an action grant. The program owner may revoke their own grant even when another eligible member sponsors the room. Handoff changes the sponsor revision and requires explicit re-admission; it never transfers the document, unused grant or trial history. On room expiry, refund, membership loss, owner revoke, disconnect or Emergency Stop, reject new effects, cancel uncommitted work within the frozen bound, and keep independent personal and safety controls. A committed marker remains in the owner's document unless the owner separately removes it; payment expiry is not permission to erase user content.

This marker is a discrete effect with `reaction_requirement: none`; it does not need Minecraft's continuous-control or Fabric movement machinery. A first-party guest makes an explicit bounded request and sees the attributable result; in the optional MCP variant, the guest's own Codex client chooses whether to call the tool and reasons over the returned observation. Helix admits identity, grant, bounds and provenance; the connector applies the native mutation and reports the postcondition. Do not turn a receipt into the final answer or create a second sampling loop. The [environment reasoning contract](../architecture/helix-environment-agent-reasoning-v1.md), [adapter registry](../architecture/helix-environment-adapter-registry-v1.md), [CFP-3 delegated-action packet](eh-g8-cfp3-shared-program-action-delegation-v1.md) and [G8 program](../helix-environment-harness-work-program-v1.md) govern the later implementation. ## Acceptance and dispatch fence

CFP-1 must freeze the selected action ID/version, customer task and wording, exact program/document/owner/requester identities, grant fields, result/postcondition, effect unit, paid/trial operation set, artifact/connector versions and rights disposition. CFP-3 then implements the admitted action profile and owner-issued one-use grant without weakening the current self-player or read-only paths. CFP-4 proves on two physical client devices that a distinct guest requests the effect without a guest model account, the owner's native document changes once and both permitted views attribute the result. If the optional MCP path is selected for customer copy, separately prove that its tool result re-enters the guest's own external reasoning turn.

Negative cases: no grant; forged or wrong owner, requester, room, sponsor revision, node, document, coordinate, version or connector epoch; stale document revision; concurrent double use and replay; expired trial/paid term; lost membership, consent, source, lease or program owner; revoke during execution; direct MCP/API/service bypass; restart, reconnect and explicit handoff. At most one native marker may result from one grant. A fresh postcondition, not a queued request or UI toast, determines a successful effect. Preserve the free personal comparator for never-subscribed and expired-hosted owners. If an external program is selected instead, replace the marker-specific terms with that program's real native effect and rights/installed evidence before dispatch.
