# CFP-1 Fabric package and runtime identity contract v1

The [source crosswalk](../evidence/eh-g8-codex-first-paid-product-delivery-v1/cfp-1/2026-09-20-cfp1-fabric-player-package-identity-crosswalk-161.md) found three distinct labels: code-owned directory package `com.casimirbot.minecraft.fabric-player:0.4.0`, development mod `HelixFabricPlayerAgent-0.4.12.jar`, and action-manifest adapter `0.4.11`. The [later route audit](../evidence/eh-g8-codex-first-paid-product-delivery-v1/cfp-1/2026-09-20-cfp1-fabric-player-pairing-route-split-176.md) corrects their relationship: the selected same-host P03 player pairing uses **one-time bootstrap `/pairing/redeem`**, not the separate package-directory `/pairing/start` and `/pairing/claim` route. The Java client sends `0.4.11` as `connector_version` during bootstrap redemption and later in its action manifest; no directory `package_version_id` is sent on that P03 path. This packet specifies proof for the actual bootstrap/JAR/manifest/action-catalog relation and treats the `0.4.0` directory package separately. It declares no current signed-byte compatibility or accepted ordinary-user effect.

The [D03 technical freeze](eh-g8-cfp1-conditional-minecraft-shared-action-freeze-v1.md)
records why the current development player/action pair cannot support the

## Release-input mapping to freeze

For each proposed **P03 local-player release tuple**, record the one-time bootstrap route and action-credential/authority/installation identity; planned player and sensor mod IDs/versions; embedded connector-core library coordinate/version (`com.casimirbot:helix-minecraft-connector-core:0.2.0` in the current build scripts); actual packaged JAR and nested core-byte hashes when built; action and observation manifest schemas/protocol/adapter versions; the admitted action capability-catalog snapshot, adapter profile/contract hash and selected capability IDs/versions; Minecraft/Fabric/Java compatibility; and rights/provenance for every shipped byte. The player and sensor build scripts both use `include(connectorCore!!)`, so the core is an embedded library identity in each mod artifact, not a third mod. The mod and adapter versions may differ only when their distinct meaning and compatibility are explicitly verified; do not infer validity or failure from string equality alone. A development JAR hash is an inspection baseline, not the release-byte choice. CFP-1 freezes planned identities and compatibility/denial rules; CFP-2/3 verify actual built/installed hashes and observed manifests before accepting the cases.

The [C07 nested-core byte inventory](../evidence/eh-g8-codex-first-paid-product-delivery-v1/cfp-1/2026-09-20-cfp1-c07-fabric-nested-core-byte-inventory-185.md) shows that both **local development** mod JARs contain the same embedded core archive. Its raw archive hash differs from the standalone core JAR because the embedded archive adds generated Fabric metadata; all 63 shared ZIP entries have identical uncompressed content. For the reserved customer build, hash each mod JAR and its extracted **nested** core archive, inspect its metadata, and compare its expected contents and build provenance under an explicit rule. Do not require raw nested and standalone archive hashes to match or treat this development comparison as signed-byte proof.

The [customer delivery/profile contract](eh-g8-cfp1-c07-customer-connector-delivery-and-profile-contract-v1.md) closes the **planned** acquisition boundary left by the [source gap](../evidence/eh-g8-codex-first-paid-product-delivery-v1/cfp-1/2026-09-20-cfp1-c07-customer-provisioning-source-gap-189.md): current desktop profile selection, developer mod-copy equality and lifecycle log checks do not authenticate installed mod bytes. The first-cohort proposal ties separately published first-party JAR assets to a reviewed release allowlist in the signed EXE or equivalent authenticated manifest, uses customer-owned game/Fabric prerequisites, and requires a dedicated accepted profile with pre-launch/restart hash and loaded-manifest proof. This is an acceptance target, not a current verifier or approved delivery route.

The **separate directory/device-pairing path** uses `pairing/service.ts`. Its `packageContentHash` covers package ID/version, adapter profile, host compatibility and capability descriptors, **not** JAR bytes. `ensureBuiltinEnvironmentConnectorPackages` inserts with `ON CONFLICT (package_version_id) DO NOTHING`, so an older persisted row may remain under the same ID. The current public directory route seeds and lists built-in rows, so D12 must either **retain and review the `0.4.0` public row** or explicitly filter/exclude it for the first-customer service. If retained or if directory pairing is selected, compare code-owned and persisted package ID/publisher/version/content hash/compatibility/descriptors/trust state, and fail closed or perform an explicitly reviewed version/migration on mismatch. Do not make this persisted-row check a substitute for P03 bootstrap/JAR/manifest proof or claim that P03 currently calls `/pairing/start`.

The [full public-directory scope audit](../evidence/eh-g8-codex-first-paid-product-delivery-v1/cfp-1/2026-09-20-cfp1-public-directory-package-scope-audit-178.md) finds five built-in package IDs, with no first-customer allowlist on listing or generic pairing. The [provisional five-row D12 matrix](eh-g8-cfp1-public-directory-first-cohort-scope-v1.md) excludes Paper, Fabric sensor, Fabric player and synthetic fixture from public generic directory/device use, with system-clock conditional on C10 review and clean external acceptance. The [sensor/player route check](../evidence/eh-g8-codex-first-paid-product-delivery-v1/cfp-1/2026-09-20-cfp1-fabric-sensor-and-directory-scope-191.md) shows both selected local Fabric paths use one-time bootstrap rather than a directory package ID; their JAR/manifest and rights proofs remain separate. Directory exclusion must fence direct start and pending approve/claim as well as GET, and revoke/fence previously claimed credentials or check versioned package eligibility at every later device/probe admission. A hidden row alone is not exclusion or final D12 acceptance.

The action broker separately hashes and admits the submitted action manifest against action capability/profile/authority data and checks its **action catalog snapshot** before an effect. That snapshot is distinct from the package-directory row. Runtime manifest admission is **not** proof of which JAR bytes produced it. The release/install path must independently establish installed JAR provenance/hash and link the observed manifest to the reviewed bootstrap compatibility mapping and connector epoch. A bootstrap credential, server `approved` trust classification or authenticated device key alone is not a commercial-rights decision or signed-byte attestation. If the selected installed JAR emits a version or capability set outside the mapping, selected actions fail closed with typed recovery; no fallback to another local mod or unreviewed directory label.
