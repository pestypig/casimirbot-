## Client profiles and mission routing

CasimirBot has one capability, evidence and permission model exposed through
several client profiles. A profile identifies how a request enters the system;
it does not grant authority or promise equivalent context, reasoning quality or
continuation behavior.

| Client profile | Intended use | Qualification boundary |
| --- | --- | --- |
| Bound external Codex task | Preferred sustained personal mission workspace and a candidate room mission principal. | Exact task/owner binding, durable continuation, tool-result re-entry, stop/revoke and reconnect evidence. A customer's Codex or ChatGPT subscription is never shared with room members. |
| Ordinary ChatGPT text/plugin entry | Discovery, account or goal setup, status, attributed steering and later qualified bounded operations. | Use only capabilities admitted for that surface. It may invoke a bounded skill directly only under the routing rule below; it does not inherit another task's chat history or authority. |
| Website-hosted Helix/Codex surface | First-party presentation of permission-filtered mission state and, if later selected, managed reasoning. | Managed-session identity, payer, context release, usage, continuation and terminal-authority evidence. UI presence is not proof of reasoning or execution authority. |
| Managed Agents API backend | Candidate managed mission principal or restricted worker behind a first-party experience. | AR evaluation and a separate offer decision; no private duplicate sampler, tool loop or provider-account transfer. |
| Shared GPT Live participant | One conversational participant for a room, capable of delegating selected work to an application backend. | Speaker/room identity, consent, interruption, revision fencing and result-return evidence. It may be the mission principal only when its bound backend independently meets the principal contract. |

Route each request by the authority and continuation it needs:

1. A client may inspect, explain or propose within its current read scope.
2. A qualified bounded-skill caller may invoke a skill when that operation can
   finish, fail or hold honestly without a later strategic decision and does
   not bypass an existing mission principal.
3. A small change to an existing mission steers its current principal with the
   speaker, mission revision and evidence identity preserved.
4. Work that requires continuing semantic choices must have exactly one
   qualified mission principal. Restricted workers return evidence or proposals
   to it; they do not become competing principals.
5. Principal handoff is an explicit checkpointed transition with old-authority
   revocation and revision continuity.
6. The program owner can always stop, revoke or take over through the direct
   local control path without waiting for a reasoning client.

All profiles may call the same admitted underlying skill implementation, but
each receives only permission-filtered task context: selected environment and
subject, operation identity, policy and grants, current observation revision,
relevant failures, mission binding and allowed history. Shared execution
machinery does not imply shared chat history, permissions, decisions or model
performance.

## Governed skill-operation technical spine

A useful environment capability is a stateful, governed operation rather than
a stream of remote key presses. The complete product loop is:

```text
fresh observations + relevant procedural/task memory
  → permission-filtered context and available actions
  → principal-selected objective, skill and policy
  → admitted skill operation with a stable operation reference
  → bounded route/behavior plan and finite execution segment
  → local scheduler/controller with reactive supervision
  → measured checkpoint and native result
  → recovery, hold, completion or revision-fenced replanning
```

The operation reference survives a permitted reconnect; authority never does.
Every dispatch revalidates the current owner, subject, connector epoch, grant,
mission revision, observation freshness and cancellation state. The controller
may repair locally only within the selected destination, traversal rules,
effects, risk limit, deadline and declared repair permission. A change of goal,
risk or program ownership returns to the mission principal or owner.

The implementation optimizes a **valid execution runway**: the current finite
segment may run while the next candidate is prepared, but the candidate is
revalidated after planning and immediately before dispatch. It does not seek a
large stale queue, ask a model for every tick or encode every possible world
state as a fixed decision tree.

Every ongoing operation reports four independent status dimensions:

| Status dimension | Required examples |
| --- | --- |
| Work progress | admitted, planning, executing, holding, recovering, complete, failed or outcome unknown |
| Physical control | owner/manual, controller active, stop requested, stopped and released, disconnected |
| Evidence | fresh, stale, conflicting, unavailable and last measured revision |
| Reasoning delivery | principal responsive, worker pending, proposal returned, revision accepted/rejected, provider unavailable |

Procedural knowledge, mission history and current observed state are stored and
identified separately. Learned or generated components can propose plans or
policies, but a trusted admission and execution boundary remains responsible
for effects and evidence.

## Assisted-room acceptance scenario

AR-2 uses one stable scenario so API connectivity is not mistaken for useful
collaborative reasoning:

1. Dan hosts; Sam and Alex join as distinct authenticated members. If the
   current two-person room limit remains, first use a deterministic fixture and
   then run live only after an admitted capacity change.
2. The room explicitly starts one shared OpenAI-backed participant and records
   the development provider project, consent, usage owner and session identity.
3. The room binds one exact mission principal: either a qualified external task
   or the qualified backend behind the shared participant. Starting GPT Live
   alone does not select a principal. The shared participant and any restricted
   workers cannot become competing principals or environment writers.
4. Dan states a mission. Sam adds a safety constraint. Alex proposes a route.
5. Sam corrects a wrongly attributed or unsafe interpretation. The participant
   preserves the speaker, updates the visible mission and does not convert the
   correction into an effect.
6. Permitted program evidence enters the principal's reasoning lifecycle. Any
   worker result returns to the same conversation with its source and applicable
   mission revision. The visible chain advances through request submitted,
   request received, decision returned, action admitted and native result
   verified. A member request remains a proposal until the actual program owner
   grants the exact action.
7. The connector executes once. The native observation returns to the same
   mission and the room reports actual outcome, uncertainty, source and whether
   the result changed the mission.
8. Owner revoke, member departure, provider failure and reconnect preserve
   history without retaining effect authority. A second room is denied.

This scenario evaluates product behavior. It does not show that the initial
subscription includes OpenAI usage, that a ChatGPT/Codex subscription funds an
API session, or that current two-member experimental room code is commercially
ready.

After serialized authority is accepted, a separate cooperative extension may
evaluate independently owned actors executing nonconflicting admitted segments
at the same time. It must define per-actor stop, conflict, proximity/following,
moving-target and partial-failure semantics. It is not permission to weaken the
current one-lease rule or to claim three-player hands-free operation now.

## Developer and catalog contract

The first public artifact is the selected read-only interoperability package.
It includes the reviewed contract symbols, TypeScript/Java helpers, read-only
template, system-clock example, deterministic fixtures, schema-parity command,
package identity, compatibility and removal guidance. It does not expose a
generic action loader or grant a manifest trust.

The signed base harness provides the runtime, account, catalog, connection,
grant, evidence and lifecycle surfaces. It does not need to contain every
program connector. Reviewed connector implementations remain separately
identified packages so a user installs only the programs they intend to use.

The catalog experience must distinguish:

```text
discover → download/obtain → install → enable → connect
  → personally authorize → optionally expose to a room
  → issue bounded action grant → execute → observe/recover
```

Each listing states publisher, immutable package/version identity, supported
program versions, observation/action status, required permissions, outbound
data, personal/room support, rights/review state, support window, changelog and

A repository branch is a development input. A catalog release is a reviewed,

## Environment Home, package source and execution profiles

The product target is a permanent **Environment Home** workstation panel that
uses a controller-friendly tile grid inspired by a console channel menu. It is
the stable first panel for both account modes; developer accounts retain their
full panel and control superset. Built-in tiles include Environment Store,
Account, Local Harness and supported first-party environments. Installed
connector packages add tiles through reviewed metadata; they do not patch the
EXE or add themselves to the static panel registry as trusted code.

Each environment tile shows its package/version, install and connection state,
current subject, evidence freshness and active operation. Its overflow menu may
open details, update/remove controls and **Execution Profiles**. It must not
display, retain or submit raw provider keys from ordinary renderer state.

The product separates five objects:

| Object | Responsibility |
| --- | --- |
| Catalog record | Publisher, source repository, immutable release/commit, license and rights state, compatibility, permissions, review, lifecycle, artwork and artifact hashes. |
| Installed connector package | Versioned adapter code and declared capabilities installed outside the signed EXE, scoped to one owner and device. |
| Execution Profile | Selects admitted reasoning roles and runtimes for that environment, such as external Codex over local MCP, a user-funded Agents API session, or a reviewed planner/action-selector combination. It never grants program authority. |
| Credential Connection | An owner-scoped opaque reference to an OS-protected or provider-vault credential. The native broker releases it only to the exact admitted package, provider, role and operation. |
| Runtime supervisor | Starts, monitors, stops and receipts isolated package processes under declared filesystem, network, command and resource policy. The existing secret-bearing developer “opaque launcher” is an implementation precedent, not a customer configuration surface. |

### GitHub-backed package policy

GitHub is the preferred public source and artifact channel for reviewed open
developer integrations, but the Store is not a generic GitHub browser or a
`git clone` button. Admission pins an immutable commit and, when executable
bytes are distributed, an immutable release asset plus SHA-256, signature or
reviewed provenance. Installing a mutable branch, executing arbitrary repository
setup instructions, trusting a README, resolving floating dependency versions
or treating public visibility as a redistribution license is prohibited.

The domain database continues to own publisher identity, catalog presentation,
review decisions, supported versions, permission declarations, compatibility,
withdrawal and installation/account references. It need not proxy public
package bytes. A withdrawn or compromised GitHub release must still be denied
by CasimirBot admission and by already-installed package cutover policy.

Package artwork may derive from a reviewed repository asset. The harness
fetches and caches only pinned, size-limited image content with a verified hash;
repository HTML, scripts and remote styles never become workstation UI. The
first implementation should use a generic environment detail/configuration
panel. Arbitrary third-party React panels or other in-process UI plugins require
a later sandboxed UI contract.

### Required lifecycle proof

The later GitHub-backed Store and Execution Profile slice must prove:

```text
discover reviewed record → inspect source/license/permissions
  → fetch immutable artifact → verify hash/signature/provenance
  → install in isolated owner scope → create tile
  → bind credential reference and execution profile separately
  → start supervised runtime → connect and inspect capabilities
  → authorize subject/effect → execute and measure
  → stop/revoke/rotate/update/rollback/uninstall
```

Negative evidence includes mutable-branch drift, missing license, changed or
deleted asset, hash/signature mismatch, unreviewed install script, floating
dependency, credential leakage, package-to-package credential access, excessive
network/filesystem requests, incompatible host version, withdrawn release,
stale running process and removal with retained authority.

## Experience states and failure transitions

The room and mission UI must display independent state instead of one ambiguous
“connected” indicator:

- room call health and each authenticated participant;
- shared AI absent, starting, available, degraded or removed;
- selected principal identity and responsiveness;
- mission revision, operation progress and latest verified outcome;
- sponsor/trial eligibility and bounded usage without implying action rights;
- each actor's program connection, owner, grant, controller state and current
  execution reason; and
- pending worker requests and whether their results applied to the current
  mission revision.

The controls **end mission**, **remove shared AI**, **leave room**, **disconnect
program**, **stop actor**, **revoke grant** and **manual takeover** have separate
effects and receipts. At minimum, acceptance covers these transitions:

| Failure or transition | Required behavior |
| --- | --- |
| GPT Live/provider fails | Mark AI unavailable; keep the human call and already-authorized local stop controls usable; do not invent a model result. |
| Worker or principal fails | Preserve the request and revision state; hold any work needing its decision; report whether physical control continues. |
| Actor disconnects or evidence becomes stale | Stop or hold according to the admitted connector policy, invalidate prepared segments and require fresh evidence before resuming. |
| Sponsor loses eligibility or budget is exhausted | Deny new sponsored reasoning/hosted capacity, preserve account and personal harness access, and allow explicit eligible-host handoff where selected. |
| Owner takes manual control or revokes | Reach a measured stopped/released state directly; cancel or invalidate pending dispatches and proposals. |
| Package is updated, withdrawn or incompatible | Block new admission, preserve diagnostic identity and follow the tested update/rollback/removal policy. |
