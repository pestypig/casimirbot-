## Candidate customer task and independent authority

An authenticated host invites one distinct account to a room. The host owns a connected Minecraft player and explicitly grants that guest one finite, exact-target action. The guest uses their own supported reasoning client to request removal of one approved reachable stone block, then both people see the attributable native result. The companion [personal two-block proposal](eh-g8-cfp1-bounded-assistance-acceptance-v1.md) supplies useful bounds but is **not** a hosted acceptance result: its subject is one owner with no other member, and its stationary/no-approach rule is not yet enforced by the mine schema. A hosted variant needs its own grant, attribution, rights and two-account fixtures. The first paid release may instead select a different rights-cleared connector/action if this candidate fails review.

Keep the following axes separate at every call: verified account/client; current sponsoring host's paid eligibility; room membership and role; each participant's processing consent where applicable; program owner, source, player and exact action grant; current connector manifest, lease and native effect result. A payment, invite, OAuth scope or room consent receipt alone is never a program grant. `room.consent.grant` in the current room contract covers microphone, transcript, screen and model-audio fields; it is not the Minecraft action grant. The current action broker **hard-denies** a guest acting on the host's paired player: `resolveEnvironmentActionAuthorityBase` requires a non-owner's membership participant ID to equal the paired participant, and action enqueue requires the requester to equal the action request's participant ID (`server/services/environment-connectors/actions/action-broker.ts`, around lines 2971–2984 and 3397–3413). Current authority configuration is for the paired subject/participant and stores allowed capability IDs and expiry, not a guest-requester, exact-target, one-use delegation (`server/services/environment-connectors/actions/authority-store.ts`, around lines 618–703). It also requires the authority configurator to be both room owner and environment owner, so a guest who owns a separate program cannot configure its player merely by joining (`authority-store.ts`, around lines 618–653). Both ownership arrangements require new admission contracts; room membership plus owner configuration cannot satisfy this candidate today.
