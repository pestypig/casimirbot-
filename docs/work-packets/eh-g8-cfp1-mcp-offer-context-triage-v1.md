## Decide an operation in a context

Do not implement entitlement as a paid/free Boolean on an MCP name. The same tool can operate on the owner's personal context without a hosted term and on another owner's explicitly shared program inside an eligible paid room. `helix_minecraft_player_action` is the concrete example: the selected context, participant, player, owner grant, current lease and connector determine effect admission. A subscribed host cannot buy another person's action authority. Conversely, cancellation cannot disable the owner's independently authorized personal use or direct stop/revoke.

The eventual supported-offer register therefore needs a row for each selected `(release artifact, MCP surface, tool name, operation/verb, capability ID and version, context kind)` combination. Record the account and external-client profile, OAuth scopes, setup route, payer/guest rule when hosted, membership, owner/subject/source bindings, consent, effect limits, rights disposition, positive/negative tests and customer wording. Split multi-operation tools such as workflow control: `resume` may require current action authority while `cancel` and `emergency_stop` need an expiry-safe owner path. A safety/status lane is still identity and target scoped; it is not anonymous or unbounded access.

### Source-backed exceptions that must survive selection

- The current base `user` policy locks shared rooms and source ingress. The public-room experiment requires both server enablement and stored account enrollment, with additional source-ingress conditions. It is not subscription admission. The full environment MCP action/status scope arrays include room read, and many handlers require a room ID. An internal owner-only personal context or separately reviewed personal binding must satisfy the free journey without granting paid-room authority.
- Current `helix_room_source_list/create` MCP actors use external OAuth while nondeveloper source management requires a first-party session. A free owner source wizard needs its own reviewed route; the source registrations do not prove ordinary-user MCP source setup. `helix_room_presence_set` currently requests Minecraft action scopes and needs a reviewed generic-room scope before any broad presence claim.
- `helix_minecraft_local_lifecycle_launch` currently checks for a developer account even when a player authority exists. `helix_minecraft_situation_probe` has no coordination-shadow equivalent. Eight private companion evidence tools are conditional and are not a public catalog promise. The inspected 43 environment/Minecraft names contain no exclusively paid coordination tool; 10 personal candidates and five safety/status names may need distinct personal and hosted context rows **where applicable**. Local lifecycle launch remains an authenticated owner's device operation, not a way for a paid participant to start someone else's device.
- Five local-supervisor names describe installed-node presence, coordination and relay, not an unrestricted external task bridge. The reasoning prompt queue has separate delivery, pickup and applied-decision states; ordinary MCP access does not prove wake or steering of an existing external task. Keep the basic personal tool loop useful without that bridge.
- `helix_run_continue` cannot silently supply CasimirBot-funded reasoning. Six brokerage names, three realtime texture names, six Surface Registry names, four visual-sequence names and three desktop tunnel transitions remain specialist or developer-scope review items at this HEAD. A brokerage read or source registration does not make these general public personal tools.
- Full MCP handlers and coordination-only shadow registrations must be compared independently. A shadow may appear in a catalog but fail closed. The owner cannot select a customer benefit from source-name presence, a descriptor or a developer fixture alone.

The [personal/hosted capability boundary](eh-g8-cfp1-personal-hosted-capability-boundary-v1.md), [hosted participant lifecycle](eh-g8-cfp1-hosted-participant-entitlement-lifecycle-v1.md), [claims register](eh-g8-cfp1-claims-evidence-register-v1.md) and [current payment-to-effect trace](../evidence/eh-g8-codex-first-paid-product-delivery-v1/cfp-1/2026-09-19-payment-to-minecraft-effect-source-map-15.md) retain the detailed authority and release holds. ## Owner selection and executable handoff

The product owner and MCP/account owners must identify every operation actually promised for the first release, including non-Minecraft families, and mark each selected context row with its handler, version and evidence owner. The selection must include the complete supported personal set, not just the bounded Minecraft proof of concept; it may honestly mark specialist and shadow tools unavailable while preserving the broader G8 catalog-parity goal. The owner selected [one host sponsoring invited guests](../evidence/eh-g8-codex-first-paid-product-delivery-v1/cfp-1/2026-09-19-host-sponsorship-owner-selection-21.md) and an [action-inclusive first paid benefit](../evidence/eh-g8-codex-first-paid-product-delivery-v1/cfp-1/2026-09-19-shared-actions-benefit-owner-selection-26.md); select exact room/action rows and freeze the transfer rule before hosted rows are accepted. All rows in the companion worksheet stay `unselected` until exact capability decisions and installed acceptance are recorded; do not convert a candidate lane into an acceptance status by bulk edit.

The [first paid shared-action candidate](eh-g8-cfp1-first-paid-shared-action-candidate-v1.md) traces one room/invite/guest-action/stop path to current handlers and required tests. It remains a proposal because neither the exact release rows nor Minecraft commercial rights are cleared. The owner [selected an action-inclusive trial shape with trial-specific limits](../evidence/eh-g8-codex-first-paid-product-delivery-v1/cfp-1/2026-09-19-trial-shared-action-benefit-owner-selection-42.md); this candidate does not replace the 104-name worksheet or select exact paid/trial rows and limits.

adds source IDs, catalog descriptor versions and authority/test obligations for

For CFP-2.PUBLIC/ONBOARD, capture real installed full and coordination-only `tools/list` results for an ordinary never-subscribed and expired-hosted account, then exercise each advertised personal row through the actual setup, success, wrong-owner, stale lease, revocation and reconnect cases. CFP-3.LICENSE/COMMERCE applies hosted eligibility per selected room operation while preserving the same personal counterexamples and safety paths. CFP-4.INTEGRATION repeats the accepted hosted rows with distinct members, program owners and devices; a paid room still needs an explicit program grant and native effect result. Where the same tool serves two contexts, test both directions: no hosted grant from a personal call and no personal paywall from hosted expiry. Verify direct API/MCP/service paths as well as UI presentation.

This triage does not close CFP-1. Owner selection, a declared first client and
frozen installed-catalog acceptance tests, O-01–07 commercial terms, and
R-OWN/R-MC/R-PUBLIC dispositions still govern the CFP-1 specification freeze.
CFP-2 then supplies actual ordinary-user installed catalog/effect evidence;
CFP-3/4 verify the signed artifact and remaining G8 prerequisites before
customer claims or release. Future installed output cannot serve as evidence
for closing its preceding specification stage.
