# CFP-1 Google P1 fresh-auth feasibility v1

## Source and provider boundary

The [current source audit](../evidence/eh-g8-codex-first-paid-product-delivery-v1/cfp-1/2026-09-20-cfp1-google-fresh-proof-source-audit-183.md) found Google Identity Services `auto_select` sign-in followed by `/api/auth/google`: the server verifies the token audience and stable `sub` for a CasimirBot web session but does not request or check `auth_time`, nonce or a sensitive-operation intent. The existing Auth0 step-up is for a developer/native desktop session and does not establish ordinary `user` Google enrollment. Neither a recent CasimirBot cookie nor an ID token's `iat` proves a recent Google authentication.

[Google's Security Bundle documentation](https://developers.google.com/identity/siwg/security-bundle) now documents `essential_claims: "auth_time"` in the **existing GIS Web JavaScript API**, as well as an OIDC `claims` request. The signed `auth_time` describes the last Google Account authentication on that browser/device, distinct from token `iat`. This feature requires a published, verified Google app and enabled Session age claims; missing claims may reflect disabled settings. The current CasimirBot client has not been shown to meet those prerequisites. Google explicitly says it does not support Google Account reauthentication requests. A claim request can therefore observe a stale Google session, but cannot force it to become fresh. [Auth0's federated-login warning](https://auth0.com/docs/authenticate/login/max-age-reauthentication) also says a new Auth0 `auth_time` may record an upstream exchange without a new Google authentication. The [dated correction](../evidence/eh-g8-codex-first-paid-product-delivery-v1/cfp-1/2026-09-20-cfp1-google-security-bundle-source-correction-256.md) supersedes the earlier packet's assumption that a separate Google code flow is needed to *request* the claim; it does not establish a reachable fresh Google-only step-up.

## Candidate proof flow to qualify, not present support

1. The signed P1 wizard or domain account page starts a server-side, short-lived intent for one exact purpose, target device/recovery generation, profile and service epoch. Retain an opaque nonce/intent verifier server-side. Do not place a reusable P1 or model credential in a browser flow.
2. If Google Security Bundle is enabled for the verified production app, test the documented GIS `essential_claims` and `nonce` route with the existing Google `sub`; validate the signed ID-token issuer, audience, expiration, nonce, stable provider `sub` linked to the initiating active CasimirBot profile, and replay/intent expiry server-side. A separately reviewed code flow remains an option, not a prerequisite just to request `auth_time`. Neither route forces a stale Google session to reauthenticate. `login_hint` or account selection may help select the expected account but never substitutes for the checked `sub` or freshness.
3. If the Google claim is offered as freshness proof, accept it only if a valid signed `auth_time` satisfies the account/security owner's selected window and intent-binding rule. To align with [source audit 183](../evidence/eh-g8-codex-first-paid-product-delivery-v1/cfp-1/2026-09-20-cfp1-google-fresh-proof-source-audit-183.md), the **proposed, not approved** Google-claim predicate is authentication no older than five minutes **and no earlier than the operation intent's creation**, except a bounded, documented clock-skew allowance; the single-use receipt lasts at most two minutes. An issued-now token with an old, absent, future or malformed `auth_time` fails this Google-claim path; neither `iat` nor an account-picker/consent prompt repairs it. A separately reviewed step-up needs its own signed/verified challenge result, freshness and intent-binding predicate, rather than pretending its result is a Google `auth_time`.
4. Mint a receipt bound to account, purpose, target installation/device generation, profile, session and service epoch. Consume it once at the exact enrollment/recovery/scope/payment/deletion endpoint. A successful receipt still does **not** grant native program effects; the separately approved P1 client grant, device binding, program-owner grant and connector checks remain required.
5. If the Google result is stale or cannot carry the claim, deny the sensitive mutation **until** a separately accepted step-up succeeds, with a clear recoverable state. Preserve existing independently authorized inspection and stop/revoke. Do not loop silent Google redirects or tell a Google-only user to sign into an unrelated account. A first-party authenticator or formally linked identity step-up may provide recovery, but its initial enrollment trust, loss and `sub`/profile binding must be proved before it becomes the fallback.

The ordinary GIS sign-in remains useful for account identity and browser sessions under the [D02 lifecycle proposal](eh-g8-cfp1-public-session-and-client-grant-lifecycle-decision-v1.md). Requesting `auth_time` on GIS would add a trust signal, not a guaranteed step-up. This packet does not assert that Security Bundle is enabled, a reachable fresh Google-only result or a recovery authenticator already exists in CasimirBot.

## Existing Auth0 seam to qualify

The [read-only source and test recheck](../evidence/eh-g8-codex-first-paid-product-delivery-v1/cfp-1/2026-09-20-cfp1-d02-auth0-linked-step-up-source-seam-258.md) found a narrower possible implementation path. The installed Auth0 account-link flow accepts an active CasimirBot account session and authenticated native desktop session, uses PKCE and a verified Auth0 subject, and writes that subject to `helix_account_linked_providers` under the initiating profile after rejecting a cross-profile conflict. A Google-owned profile can therefore **potentially** hold a distinct Auth0 identity without merging on email. The Auth0 step-up controller checks the active session's linked Auth0 subject and signed MFA/freshness claims, but its exposed route requires `developer` account policy and the native installed-services surface. The link and step-up suites pass deterministic tests; no ordinary-user, Google-only enrollment/recovery or configured-tenant trace was run.

Qualify this as a **candidate independent Auth0 MFA challenge**, not fresh Google authentication and not a public route already present. A CFP-2 spike must prove that a Google-only owner can establish the linked Auth0 identity under a reviewed initial trust rule, enroll an approved factor, complete an operation-time MFA challenge and recover after factor/device loss without a developer role, a second unlinked CasimirBot profile or an email-based merge. The result must bind the exact Google-owned profile, Auth0 subject, P1 intent/device generation and single-use receipt. The current controller's `acr`/`amr`/`auth_time` checks do not by themselves prove that a new factor challenge occurred **after** this operation intent; tenant Action/configuration and a redacted live factor-event trace must establish that separately. A Google-social Auth0 exchange or recently updated Auth0 `auth_time` alone cannot satisfy the factor event. Require negative fixtures for wrong subject, previously linked subject, stale/replayed challenge, linked-provider revocation, account switch and native-session loss. Check the actual Auth0 tenant's factor/plan availability and per-user cost as D07 inputs before choosing this route. [Auth0's step-up documentation](https://auth0.com/docs/secure/multi-factor-authentication/step-up-authentication) supports an MFA challenge pattern; its [federated reauthentication warning](https://auth0.com/docs/authenticate/login/max-age-reauthentication) remains controlling. If this candidate cannot provide a reachable, fairly priced first-enrollment and recovery journey, compare a first-party authenticator under the same proof and recovery tests rather than promoting the existing developer endpoint to `user`.

The [conditional small-cohort cost screen](../evidence/eh-g8-codex-first-paid-product-delivery-v1/cfp-1/2026-09-20-cfp1-auth0-step-up-small-cohort-cost-screen-264.md) now prices the publicly displayed Auth0 Essentials/Pro MFA scenario alongside one illustrative signing account. It is not evidence that this tenant needs that tier: Free lists passkeys but not Pro MFA Factors, and tenant/flow availability remains to verify. D02 must identify the exact factor and enrollment/recovery route before D07 can assign a provider cost; neither an uncosted paid factor nor an unproved free passkey path can close the Google-only P1 contract.

The later [authenticated tenant-plan read](../evidence/eh-g8-codex-first-paid-product-delivery-v1/cfp-1/2026-09-20-cfp1-auth0-current-plan-and-mfa-entitlement-read-277.md) establishes a narrower current fact: the owner's team is on Free, its comparison excludes Pro MFA from Free, and the tenant displayed a current-month Pro MFA over-limit warning. This does not prove a particular login failure or force an upgrade. It rules out treating the existing Pro MFA candidate as a demonstrated zero-cost, continuously entitled public step-up. Qualify an available factor and recovery route under the same operation-bound tests, then feed the actual plan/cost to D07.

The [passkey-versus-MFA source screen](../evidence/eh-g8-codex-first-paid-product-delivery-v1/cfp-1/2026-09-20-cfp1-auth0-passkey-versus-mfa-source-screen-279.md) makes the Free-plan alternative testable: Auth0 documents passkeys for database connections, separately from Google social login, and requires an alternate method for database passkey users. Thus a linked database passkey needs its own trusted identity-link, challenge-after-intent, alternate-method, recovery and cost proof; it is not the existing Pro MFA event or an automatic free Google-only step-up. The tested linked Auth0 MFA seam remains the first technical qualification candidate with a paid-plan D07 branch. If it fails cost, reachability or recovery, compare linked database passkey and first-party WebAuthn under the same GP-02/GP-11 security and usability bar, rather than silently changing the proof policy.

The [first-party source boundary](../evidence/eh-g8-codex-first-paid-product-delivery-v1/cfp-1/2026-09-20-cfp1-first-party-fresh-proof-source-boundary-281.md) rules out another apparent shortcut: the existing email/password account creates its own profile and is not an operation-bound challenge for an already Google-owned profile. The scoped account and package search found no first-party WebAuthn/TOTP verifier. A new first-party authenticator remains an alternative only with explicit trusted enrollment, profile/intent binding, recovery, reviewer acceptance and build/support cost; do not relabel the password reset path or generic OTP input as that alternative.

## Selected D02 route and acceptance handoff

The [D02 account/security specification](eh-g8-cfp1-d02-account-security-specification-acceptance-v1.md) selects the linked Auth0 route for review: Google remains ordinary identity, while a dedicated Auth0 client uses TOTP MFA after the operation intent, an ordered Action exposes the resulting factor-event timestamp in a signed namespaced claim, and the server binds a two-minute receipt to that event and purpose. The five-second skew and five-minute age are checked at consumption. TOTP recovery code is the first-cohort recovery path; the current Free-plan entitlement and developer-only route are insufficient. Google Security Bundle availability and signed claims may still be tested as context, but no Google code-flow experiment is treated as forced reauthentication. If independent review or the configured tenant cannot prove this route, hold the **complete Google-only P1 onboarding claim** and reopen D02; ordinary verified Google web sign-in need not be described as broken.

Add: GP-08 verify published-app/Security-Bundle prerequisites and run the documented GIS Essential-claim route under an existing old Google SSO session to **observe** signed `auth_time`; stale or absent evidence denies without a new client grant, while genuinely fresh evidence proceeds only under the selected predicate and remaining identity/intent checks. Separately inject a validly signed stale-claim fixture that must deny deterministically. GP-09 an account chooser or consent prompt with an old signed `auth_time` also denies; GP-10 a wrong-subject response using the same email and a replayed nonce/intent deny; GP-11 the reviewed recovery alternative completes for the same profile/device-generation path and denies unlinked identities, loss/replay and stale receipts. A positive GP-02 must demonstrate accepted operation-bound step-up evidence for a Google-only user with stale Google SSO, not merely a new Google token or Auth0 federated exchange. Capture redacted claim names and time differences, intent/receipt revisions and signed-client trace; keep raw ID tokens and credentials out of public evidence.

No provider flow was executed for this CFP-1 specification. Google GIS claim observation is a documentation-supported **candidate**, not a configured-client or installed acceptance result, and Google does not offer an on-demand reauthentication request.
