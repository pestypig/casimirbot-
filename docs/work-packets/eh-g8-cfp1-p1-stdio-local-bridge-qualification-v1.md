# CFP-1 P1 local stdio bridge qualification v1

## First technical route to qualify

Retain the owner-selected **P1 product journey**: one Windows user runs their own local Codex desktop client and signed CasimirBot installation, approves personal scopes, uses their own program, stops it and returns without a manual connection repair or payment. Select **Codex local stdio MCP → signed CasimirBot EXE command mode → authenticated local IPC → the same installed node, catalog and admission backend** as the first CFP-2 transport to build and test. This is a qualification order, not an installed capability or a claim that the existing Electron EXE has such a command mode. The user's Codex account and CasimirBot profile/device authorization remain separate; no Codex CLI download or API key becomes a prerequisite. The separate [HTTP helper candidate](eh-g8-cfp1-p1-local-mcp-credential-and-recovery-contract-v1.md) is held unless a concrete send-time server-authenticated HTTP transport passes its wrong-listener fixtures.

[OpenAI's MCP documentation](https://learn.chatgpt.com/docs/extend/mcp?surface=cli) documents local stdio servers launched by command and HTTP servers configured by URL. It says HTTP helper headers are cached and refreshed only after a qualifying 401/403; the helper does not apply to stdio. The [read-only feasibility check](../evidence/eh-g8-codex-first-paid-product-delivery-v1/cfp-1/2026-09-20-cfp1-p1-client-transport-feasibility-159.md) and [transport choice checkpoint](../evidence/eh-g8-codex-first-paid-product-delivery-v1/cfp-1/2026-09-20-cfp1-p1-stdio-priority-decision-163.md) explain why HTTP plus a bearer helper alone cannot pass P1's cached-header port-takeover case. A Codex `identity.command` allow-list can restrict configuration identity; it is not the service's own authentication or a signature check.

The first packaging target is a **dedicated `--mcp-stdio-personal` mode of the same signed EXE**, entered before GUI startup, single-instance handling and stdout diagnostics. Codex's owned MCP entry contains the reviewed absolute executable path and fixed non-secret argument only. The mode emits only MCP protocol frames on stdout, sends sanitized diagnostics to a bounded separate channel, and never opens a second visible GUI or logs credentials. The desktop owner must prove this works from the actual packaged Electron executable; the current `apps/desktop/src/main.ts` starts desktop setup and has no stdio branch. If a separate signed helper is technically required, reopen C01/C15 packaging and notice review before selecting it; do not silently add another download or executable to the first-customer claim.

## Trust and admission to freeze

| Boundary | CFP-1 decision / CFP-2 evidence |
| --- | --- |
| Local process principal | **Selected first-cohort P1 threat boundary:** another process running as the same signed-in Windows user is within that user's local trust boundary. The bridge cannot honestly prove that its caller is the Codex UI; a command label or signed executable cannot establish that. Other Windows users, remote executors and another installed device are outside the boundary and must fail. The [D02 security specification](eh-g8-cfp1-d02-account-security-specification-acceptance-v1.md) accepts this boundary for independent review; a later stronger claim needs enforceable caller authentication and a new review. |
| IPC server identity | Prefer a per-user Windows named pipe only if CFP-2 proves owner-SID access control, first-instance/anti-squatting behavior and the server identity/connection semantics on the packaged runtime. A different same-host IPC may be selected after equivalent review. A plain loopback forwarding proxy that sends a bearer to an unverified HTTP listener is **not** the selected bridge. The bridge may pass a scoped proof only across the authenticated IPC channel; never print a token into stdout, Codex config, args, environment or logs. Deny on wrong listener, pipe name collision, wrong user, stale node generation or failed service-authentication check before issuing or forwarding any personal grant. |
| Account and device | Enrollment requires the verified Google-owned CasimirBot profile, an explicitly linked Auth0 subject, a post-intent TOTP factor event, a separately enrolled Windows installation and a fresh first-party grant of named personal scopes. The broker keeps the durable client grant in OS-protected per-user/per-installation custody; the service checks current profile, device recovery generation, grant revision and scope on every request. The [D02 security specification](eh-g8-cfp1-d02-account-security-specification-acceptance-v1.md) selects a seven-day absolute server session and a 30-day per-installation grant with same-scope renewal, subject to independent specification review and later configured-provider/installed proof. Payment, room membership or Codex login cannot supply this authority. |
| MCP and effects | Reuse the same full `createHelixMcpServer` catalog and policy projection; do not fork a smaller private tool server or treat coordination-only shadow tools as the accepted personal catalog. The IPC ingress must derive a P1 principal without falling into existing external-OAuth or native-desktop delegation. Authorization to connect never authorizes a player effect. Recheck owner source/subject, connector epoch, action lease, target, stop/revoke and effect ceiling at admission and before native release. |
| Delivery and retry | Stdio connection loss or service restart may reconnect identity, but the bridge must not replay a mutating JSON-RPC call whose outcome is uncertain. Preserve a caller-stable effect/idempotency identity through any retry and reconcile from the durable native ledger; generated trace IDs are insufficient. A changed account, revoked grant, service epoch or native authority fences new work. Stop/revoke must remain available when hosted eligibility or usage ends. |
| Wizard and return | The wizard owns only the distinct P1 MCP entry, inspects an existing entry before replacement, preserves unrelated Codex configuration and can remove its entry. No manual bearer paste or port repair. A stable reviewed launch command should survive service port rotation; the bridge discovers the current authenticated service through its IPC boundary. Ordinary-user recovery reports exact `connected`, `needs sign-in/approval`, `service unavailable`, `revoked` and `effect pending` states without restoring an expired effect lease. |

## Installed negative and recovery matrix

| Case | Required result |
| --- | --- |
| P1S-01 clean free owner | One signed installed cohort and named Codex desktop version launch the bridge without another runtime/API key; an ordinary `user` sees full allowed `tools/list`, completes a rights-qualified personal read and bounded effect, then stop/revoke. Never-subscribed and expired-host profiles retain the same personal access. |
| P1S-02 wrong local principal | Another Windows user, remote/cloud stdio placement, other device, switched CasimirBot profile or stale grant cannot inspect or execute the former owner's personal tools. Same-user invocation follows the explicitly reviewed threat boundary rather than a false Codex-process identity claim. |
| P1S-03 wrong service | Preferred pipe name collision, substituted listener, stale discovery record and service restart cannot disclose a client grant or silently connect to the wrong server. A failed IPC identity check yields a typed recovery state, not a fallback to plain HTTP or native session headers. |
| P1S-04 grant and native revoke | Revoke account/client/device during an open bridge; next request and pre-effect native release deny. Same-ID device reactivation advances recovery generation or fails closed; a prior client proof cannot become current. |
| P1S-05 uncertain and duplicate effect | Disconnect before/after admission, lose a result and repeat the same call/semantic action. Reconcile existing or pending native result; zero unauthorized second effects, including after a new stdio process starts. Stop remains independently reachable. |
| P1S-06 install and return | First setup, Codex restart, CasimirBot restart, profile switch, uninstall/remove-entry and port rotation recover or fail with typed guidance without editing unrelated MCP entries or rebinding a task. The exact command mode runs cleanly in the signed package with protocol-only stdout. |
| P1S-07 outage and scope | Domain/database outage fails closed for new issuance/effects while accurately reporting local stop status. Missing scope requires explicit approval; neither a purchase nor a hosted invite upgrades the P1 grant. |

P1S-04 and P1S-06 also exercise the [D02 lifecycle fixture](eh-g8-cfp1-public-session-and-client-grant-lifecycle-decision-v1.md): a lost renewal response after server commit and before protected custody write must recover that same successor for the same installation or enter typed fresh approval. The superseded proof cannot authorize an effect or create another successor. Sensitive enrollment/recovery consumes an operation-bound receipt only while its independently verified factor event is no more than five minutes old at consumption and the receipt is within its two-minute life; an expired initiating session or device generation denies.

CFP-1 must freeze the reviewed local-user trust choice, IPC implementation/identity rule, client-grant and server-session lifetimes, expected P1S outcomes, and the planned artifact/client tuple. CFP-2.PUBLIC/ONBOARD implement the command mode, OS custody, IPC verifier and wizard; [CFP-2.SIGNED-QUALIFICATION](eh-g8-cfp2-signed-qualification-v1.md) then supplies the independently reviewed private signed evaluation tuple for P1S-01–07 and ordinary-user traces. CFP-3 checks that a **new final signed customer artifact** contains exactly the reviewed executable mode and notices; CFP-4 repeats the selected P1 matrix on those final bytes. Capture exact executable hash/signature, Codex version and effective local placement, service hash, account/device/grant revisions, IPC server identity, `tools/list`, operation IDs, native effect evidence, expected/actual denial and first divergence. Keep D02 and CFP-1 open until their specification prerequisites are reviewed; do not convert this packet into a current support claim.

For the selected Google-compatible account journey, [GP-01–07](../evidence/eh-g8-codex-first-paid-product-delivery-v1/cfp-1/2026-09-20-cfp1-google-fresh-proof-source-audit-183.md) join P1S-01/04/06: ordinary Google auto-select login alone cannot approve the first client grant or same-ID recovery. The provider flow, OS custody and denial are later installed evidence, not current P1 support.
