# CFP-1 first-cohort public connector-directory scope v1

This is the **provisional D12 product boundary** for the customer-facing built-in package directory and generic `/pairing/start` → approve/claim → active-device path. It does not change the separate local `/pairing/redeem` bootstrap for the selected player and sensor. The [source audit](../evidence/eh-g8-codex-first-paid-product-delivery-v1/cfp-1/2026-09-20-cfp1-public-directory-package-scope-audit-178.md) found that GET currently seeds/lists all five built-ins, direct generic pairing resolves known IDs independently of GET, and already claimed credentials can remain active after a listing-only cutover. The [route check](../evidence/eh-g8-codex-first-paid-product-delivery-v1/cfp-1/2026-09-20-cfp1-fabric-sensor-and-directory-scope-191.md) confirms that both Fabric sensor and player Java clients redeem one-time local codes without a directory `package_version_id`. The release policy therefore must treat **directory** and **bootstrap** identities separately.

**Default-deny cutover rule.** A row is publicly eligible only under an explicit versioned first-customer policy after its D11 disposition and D12 claim acceptance. The same decision must govern GET projection, direct start, pending approve/claim, and *each* later active credential/device/probe admission. At cutover, already claimed excluded-package credentials, sessions, bindings and epochs must be durably revoked/fenced or rejected at the next transport admission before exclusion is described as effective. Do not remove code-owned packages or database rows merely to hide them; seeding can recreate rows and developer experiments may still need controlled access. No-session is `user` under the workstation policy; an internal/developer superset cannot leak to public callers through an unguarded route.

For a retained system-clock row, compare code-owned and persisted ID, publisher, version, adapter profile, host compatibility, descriptor set and content hash. A persisted `approved` label is not release acceptance. If drift exists, deny or perform an expressly reviewed new version/migration before public display/pairing. Excluded rows require a verified negative cutover result; they do not need a positive customer fixture or an invented commercial-rights approval simply to remain excluded. The selected personal P03/observation bootstrap must receive its own positive and negative release-tuple tests, including exact JAR and runtime-manifest proof, rather than being counted as DIR-03.
