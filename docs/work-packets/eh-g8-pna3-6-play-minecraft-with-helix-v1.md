## Product contract

The intended operator journey is:

```text
launch CasimirBot
-> Start Harness
-> restore and verify the existing exact reasoning-task binding
-> explicitly activate Play Minecraft with Helix
-> preflight exact room + source + world + player + connector epoch
-> launch/reuse the admitted Fabric profile and join loopback
-> establish or verify the separately scoped player-action lease and private pairing
-> create or restore one exact durable Minecraft monitoring goal
-> accept natural requests from Helix chat or `/helix ask <prompt>`
-> Runtime Codex selects admitted observations/actions
-> Fabric executes; fresh post-state re-enters the same solver lifecycle
-> Helix applies terminal authority once and presents the same result to text and voice
```

`Start Harness` proves only local harness and agent-connection readiness. It
does not launch Minecraft, create a goal, pair a player, or grant an action
lease. `Play Minecraft with Helix` is the distinct, explicit activation for
the displayed Minecraft objective and authority scope.

The journey is resumable rather than transactional theater. A later activation
must reuse current accepted state, diagnose the first missing prerequisite, and
continue from that stage. It must not duplicate a durable goal, rotate a
healthy identity, create a provider task, or repeat a consequential effect
merely because the renderer or EXE restarted.

## Finite readiness stages

1. `harness_required` — the full local harness is not currently ready.
2. `agent_connection_required` — authenticated client presence or current
   catalog adoption is absent.
3. `reasoning_binding_required` — no active exact task binding exists for the
   selected Helix chat.
4. `room_required` — no active room owns the Minecraft interaction.
5. `environment_required` — the exact Minecraft source/world binding is absent
   or stale.
6. `player_required` — the participant has no current selected-player binding.
7. `authority_confirmation_required` — the displayed finite player lease has
   not been explicitly accepted.
8. `minecraft_launch_required` — the admitted Fabric client is not connected.
9. `private_pairing_required` — the client has not published a current admitted
   manifest and heartbeat for the exact authority and connector epoch.
10. `agent_pickup_required` — the exact bound task has not acknowledged the
    steering event.
11. `durable_goal_required` — no nonterminal exact-environment goal matches the
    displayed objective.
12. `semantic_monitor_required` — no active monitor matches the exact goal,
    environment, player binding, producer epoch, and authority policy revision.
13. `ready` — all identities and authorities are current; ordinary Helix chat
    and `/helix ask` may enter the governed reasoning lifecycle.
14. `recovery_required` — a previously valid journey was invalidated by
    revocation, connector/world/player change, Emergency Stop, or stale evidence.

Each stage has one bounded next action and one stable reason code. After a
bounded retry budget, the journey reports manual intervention instead of
restarting Codex, opening replacement tasks, or repeating OAuth.

## Authority and terminal boundaries

- The explicit play activation may invoke only the existing loopback lifecycle,
  room owner, environment binding, player authority, private-pairing, and
  durable-goal APIs with their original policy checks.
- The objective is visible and user-editable before goal creation. Runtime
  Codex may revise strategy and milestones only through admitted durable-goal
  operations; the onboarding layer does not plan gameplay.
- Minecraft chat is an input and presentation client for ordinary Helix Ask.
  The command is `/helix ask <natural-language prompt>`; Fabric does not turn
  lexical cues into actions.
- Lifecycle receipts, progress events, steering pickups, acknowledgements,
  observations, and durable-goal projections are nonterminal evidence. Only
  the completed solver path may author the answer.
- GPT Live may read the same authorized final result. It cannot strengthen its
  certainty, select an action, or substitute for text-path acceptance.
- `/helix cancel`, `/helix emergency-stop`, room closure, reasoning-binding
  revocation, action-lease revocation, connector epoch change, world change,
  or player change invalidates the affected continuation and fails stale work
  closed.

## Deterministic acceptance matrix

Positive cases:

1. A fully ready returning installation settles directly to `ready` without a
   duplicate task, goal, lease, pairing, launch, or OAuth action.
2. A stopped but configured Fabric client follows launch -> mod load -> private
   pairing -> current heartbeat -> goal restore/create -> `ready`.
3. One natural Helix chat request and one natural `/helix ask` request retain
   the same room/player/world/task authority model and each complete only after
   current observation re-entry.
4. Browser/current-source and packaged EXE surfaces use the same endpoints,
   finite diagnosis, receipt schemas, and failure vocabulary.

Negative cases:

1. Start Harness alone grants no Minecraft authority and starts no game or
   durable goal.
2. Missing or stale exact reasoning-task binding stops before launch.
3. Wrong room, player, world, source binding, or connector epoch stops before
   pairing, goal continuation, or action.
4. Absent explicit play/lease confirmation stops before mutation authority.
5. A launch click or launch receipt alone cannot claim play readiness.
6. Duplicate activation is idempotent and cannot duplicate the goal or replay
   a game effect.
7. Revocation or Emergency Stop rejects stale pickup and releases controls.
8. A steering acknowledgement, action receipt, observation, goal projection,
   client chat line, or GPT Live utterance cannot become an assistant answer.

## EXE control-to-MCP contract

Normal play setup is expressed as typed product operations, not screen clicks.
The installed EXE and browser renderer share the same server contracts:

| User-visible operation | MCP operation | Governing boundary |
| --- | --- | --- |
| Start Harness | `helix_desktop_tunnel_transition_request`, `inspect`, and `execute` | A first-party native desktop delegation remains required; the tools cannot approve their own request. |
| Select/configure Player Embodiment | `helix_environment_subject_select` and `helix_environment_action_authority_configure` | Exact room, player, adapter capabilities, manual override, and finite expiry remain server validated. |
| Launch/reuse Fabric and join loopback | `helix_minecraft_local_lifecycle_launch` | Requires explicit operator confirmation plus an exact current active Player Embodiment lease; startup alone is not permission. |
| Private same-host player pairing | `helix_environment_player_pair_local` | Pairing code and credential never enter model context or MCP output. |
| Create/restore monitoring | `helix_environment_goal_*` and `helix_environment_monitor_*` | Exact source, world, player, producer epoch, policy revision, and continuation bindings remain mandatory. |
| Inspect/act/re-enter evidence | `helix_minecraft_situation_probe`, `helix_minecraft_player_action`, and the run evidence tools | Observations are nonterminal evidence; only Codex owns generic tool-result re-entry and completion. |
| Stop play authority | `helix_environment_action_authority_revoke` | Authority is reduced immediately and stale actions fail closed; the receipt cannot answer. |

These operations let the bound Codex task configure an explicitly requested
play session through clean MCP calls in the EXE. They do not authorize OAuth,
refresh another application's catalog, create or switch provider tasks, expose
credentials or hidden reasoning, automate Codex UI, or turn `Start Harness`
into blanket environment authority.
