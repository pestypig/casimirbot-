# CFP-1 public session and client-grant lifecycle decision v1

## Selected first-customer terms under the D02 security specification

The owner's free personal P1 journey and [selected signed stdio bridge](eh-g8-cfp1-p1-stdio-local-bridge-qualification-v1.md) require two distinct authorizations: a CasimirBot account session for identity and management, and a named per-installation client grant to connect the local MCP client. Neither confers a native program or player action. The [source gap](../evidence/eh-g8-codex-first-paid-product-delivery-v1/cfp-1/2026-09-20-cfp1-account-session-grant-source-gap-171.md) shows a seven-day cookie beside potentially unbounded server sessions and no accepted public P1 grant. The [D02 account/security specification](eh-g8-cfp1-d02-account-security-specification-acceptance-v1.md) selects the values below for independent review and later CFP-2 execution. They are not current behavior or installed acceptance.

| Boundary | Proposed CFP-1 term | Enforcement and recovery condition |
| --- | --- | --- |
| Public identity | Admit a server-verified Google or Auth0 provider subject linked to one internal CasimirBot profile. Email equality never merges profiles. Local profile selection and local developer password are not public hosted/device-enrollment identity. Other password/identity modes need their own verified-email, recovery and fresh-auth proof before inclusion. | Every web, desktop, device and hosted lookup resolves the same active profile and rejects deleted, unlinked or wrong-provider subjects. A paid term never changes `user` to `developer`. |
| Web account session | **Seven-day absolute server expiry** from each successful verified sign-in; cookie expiry is at or before the server expiry. No sliding extension from ordinary reads. A new verified sign-in issues a new session; sign-out revokes only that session unless the user selects a wider revoke. | Server queries reject expired sessions even if a cookie is still present. Account deletion and explicit all-session revoke fence the relevant sessions. An Auth0/Google provider token's expiry cannot silently lengthen the CasimirBot session. |
| Named P1 client grant | **Thirty-day maximum** from approval for one profile, Windows installation and recovery generation, named local client profile and exact scopes. Store the proof in reviewed OS-protected per-user/per-installation custody; store only a verifier/reference server-side. The signed stdio bridge passes it solely to the authenticated local IPC service, never to Codex config, stdout or another Windows user. | A server-authoritative revision, expiry, profile, generation and scope check occurs on every admitted MCP request and immediately before native effect release. A paid/trial term does not expand the grant. The grant may remain valid after browser sign-out but never after its own revoke, expiry, account deletion or device recovery. |
| Same-scope renewal | During the grant's last seven days, renew for at most 30 days only with a current verified account session, proof of the **current** client grant from that installation through its authenticated IPC path, active matching device generation and unchanged scopes. Commit one server-authoritative successor revision and deliver its proof only into that installation's protected custody. A web session alone cannot fetch or rotate another installation's proof. If the old grant/device proof is unavailable, require fresh explicit first-party approval **and a new installation-bound proof of possession** through the reviewed local enrollment path; retain the owned MCP entry and report `needs sign-in/approval` without a manual token paste or task rebinding. | Server commit and OS custody write are not one atomic operation. A lost response after commit must either recover the **same** pending successor, tied to the original renewal attempt and installation, without re-extending expiry or admitting effects under the superseded proof, or fail to a typed fresh-approval state. Before any recovery delivery, recheck pending-attempt ownership, the same active profile and current verified session, active nonrevoked device/recovery generation and unrevoked grant revision; a changed state discards pending delivery and requires fresh approval. Retrying cannot mint another successor, disclose a proof to another installation, or revive an old generation. Added scopes and a replaced/recovered device require fresh explicit approval. Program-owner effect grants remain separate and never renew from the P1 client grant. |
| Fresh proof for sensitive changes | Propose an operation-bound fresh-authentication receipt for first enrollment, same-ID recovery, scope expansion, account deletion and payment changes. The independently verified challenge/factor event must follow creation of the server-side operation intent, subject to a separately reviewed bounded clock-skew rule, and be no older than **five minutes when the receipt is consumed for the protected operation**. The single-use receipt also expires within two minutes of issuance. A newly issued provider token, Google `auth_time` observation or Auth0 federated upstream exchange is not itself evidence that the required factor event occurred after the intent. A Google-only user needs a separately reviewed, reachable step-up and recovery route, or an explicitly revised proof policy. The current Auth0-only developer route is insufficient. A verified owner must retain an accessible revoke path. | Bind receipt to exact account, initiating live session, device/recovery generation where applicable, purpose, target and service epoch; verify these both at issuance and consumption, then consume once. Deny replay, cross-account use or an event that was five minutes old at issuance but older at consumption. Account/security review must decide the challenge, its event evidence and skew bound, initial enrollment/recovery trust, whether remote device revoke also needs step-up, and provider-outage revoke behavior. These are not silently accepted here. |
| Revocation and loss | A successful revoke response requires a durable grant/device revision fence. The next MCP request and every not-yet-released native effect must deny. Stop any action still under an active native lease using its separate bounded connector stop rule; report `verified stopped` or `outcome uncertain` from evidence. | Re-registration of a revoked same device ID either rejects and routes through explicit recovery or advances generation and fences every old grant. An unreachable installation cannot be declared stopped merely because the server recorded revocation. Account switch on one Windows login clears the previous profile's projection and denies cross-profile grant use. |
| Outage | New enrollment, renewal, hosted admission and effects requiring a current server grant fail closed when the authoritative session/grant/device store is unavailable. Local stop and result inspection remain available only where the installed node can independently prove them. | No offline-effect promise is added. Browser sign-out, client-grant revoke, device revoke, program-owner stop, hosted expiry and account deletion remain distinct controls with truthful affected-scope messages. |

The thirty-day grant is a connection authorization, not a thirty-day Minecraft action lease. The seven-day web session defines management sign-in and is independent of the owner's seven-day hosted trial. This proposal minimizes repeated setup while limiting the duration of an abandoned installation credential; account/security review must accept or revise it before D02 freezes. Actual signed stdio, OS custody, IPC identity and native denial remain CFP-2/3 evidence, not assumptions supplied by the numbers.

The [hosted browser-identity audit](../evidence/eh-g8-codex-first-paid-product-delivery-v1/cfp-1/2026-09-20-cfp1-hosted-browser-identity-source-boundary-206.md) adds a distinct D02/CFP-3 case: the invited first-party [domain guest](eh-g8-cfp1-hosted-guest-request-ingress-v1.md) needs a verified account and current finite **web session**, but no P1 per-installation client grant or GPT/Codex account. Current temporary Shared Live Room `guest` sessions may join the experimental room; they must not qualify for the selected paid/trial hosted room. At sign-out or absolute expiry, deny new and not-yet-released guest effects while preserving truthful status for already released finite work. Reauthentication can recover only current membership/history under the same verified identity, not replay an old request or revive a consumed grant. Account/security review must approve the browser CSRF, cookie/domain, server-expiry and return behavior together with D02's personal-client terms.

The [cross-clock fixture](../evidence/eh-g8-codex-first-paid-product-delivery-v1/cfp-1/2026-09-20-cfp1-session-trial-cross-clock-contract-226.md) makes the seven-day **proposed** web-session life independent of the owner-selected seven-day trial: sign in at `t0`, explicitly Start Trial at `t0 + 6 days`, let the original web session expire at `t0 + 7 days`, and keep that same trial's authoritative end at `t0 + 13 days`. Session expiry must not start a second trial or reset, pause or cancel the original trial clock, room slot, PBT or native-effect counters. The seven-day trial still consumes calendar time. The expired session denies new or not-yet-released work by that actor; an already released finite effect is settled from native evidence without replay. A newly verified same-subject session may inspect current permitted room/term state but gets no new trial, resurrected request, program grant or P1 device grant. Whether a separate still-authenticated guest may act while the host's browser session has expired depends on the **independently frozen** owner-presence and program-grant rule, not on inheriting the host session. This is a proposed account/security and customer-notice fixture, not current enforcement or final acceptance of the seven-day web-session value.

The [Google fresh-proof source audit](../evidence/eh-g8-codex-first-paid-product-delivery-v1/cfp-1/2026-09-20-cfp1-google-fresh-proof-source-audit-183.md) adds a provider-specific boundary: the current Google Identity Services auto-select sign-in and `/api/auth/google` route do not request or validate `auth_time` or bind a token to a sensitive-operation intent. Keep that login for proposed account identity only. [Google's later Security Bundle finding](../evidence/eh-g8-codex-first-paid-product-delivery-v1/cfp-1/2026-09-20-cfp1-google-security-bundle-source-correction-256.md) means GIS can request signed `auth_time` once the app is verified and the feature enabled, but Google does not support reauthentication requests. First P1 enrollment, recovery, added scopes, deletion and payment changes still need a reviewed, reachable challenge and single-use operation receipt. GP-01–11 must exercise signed Google claim presence/staleness when that feature is selected **and** the positive independent step-up for a Google-only user with stale SSO; a new ID token, cookie, same email or Auth0 federated `auth_time` cannot substitute. Google remains a first-customer target, but the full P1 journey is held until that policy, provider path and ordinary-user installed cases pass.

The [Google P1 feasibility packet](eh-g8-cfp1-google-p1-fresh-auth-feasibility-v1.md) narrows the open D02 decision. Verified, enabled GIS can request `auth_time`, but its claim may report an old Google sign-in. The proposed Google-claim predicate checks age and operation-intent time with a reviewed skew bound; it applies only when Google authentication time is offered as proof. A separate step-up must have its **own** reviewer-approved freshness, subject-binding, intent, enrollment and recovery rule. GP-08–11 test stale Google SSO, deterministic claim denial, account selection, replay and the selected independent route without changing the ordinary Google web-sign-in claim.

## D02/P1S fixtures to carry forward

1. At day seven, an old cookie and server session both fail; a fresh verified Google/Auth0 sign-in creates a new server session without changing the existing valid P1 grant or subscribing the user.
2. At day 23–30, same-scope renewal requires the verified session, the current installation grant proof through authenticated IPC and current device generation. It rotates proof once under concurrent renewal, delivers it only to that installation's protected store and retains the owned MCP entry. Lose the response after server commit but before custody write: retrying the same attempt must recover only its original successor for the same installation, or enter typed fresh approval; sign-out, account deletion, grant/device revoke, a new attempt, other installation, revoked generation and old proof cannot obtain a successor after the changed state or execute an effect. A valid web session without current device/grant proof cannot renew or retrieve the credential; it must enter fresh explicit installation approval. At day 30 without renewal, ordinary tools fail with a typed sign-in/approval path; no effect dispatch occurs.
3. Revoking the grant or device during an open stdio connection fences the next request and the pre-effect release. An already released effect returns observed stop or uncertainty; there is no false instantaneous-stop claim.
4. A revoked same-ID `registerDevice`, explicit `recoverDevice`, old browser session, old IPC proof and old grant cannot restore the former generation. A second separately enrolled device keeps its own personal grant but cannot multiply one sponsor's hosted trial/capacity.
5. The Google, Auth0, wrong-subject, same-email-different-subject, local-profile and expired/deleted-account cases establish exact public identity. A first enrollment or recovery from a Google-only account must pass the selected operation-bound step-up or an explicitly revised reviewed policy before Google is advertised for the full installed journey; signed Google `auth_time` observation alone is not a guaranteed step-up.
6. Browser sign-out, client-grant revoke, remote device loss, account switch, service restart, DB/domain outage and account deletion each produce the specified distinct connection and native-action outcomes. Stop and free personal access are not removed merely because hosted eligibility expires.
7. For the hosted browser route, a verified invited guest without a P1 client grant joins and makes the bounded request under their own current session; a temporary `guest` profile, local profile selector, cookie without a matching active server session or valid same-origin/CSRF proof, wrong Google/Auth0 subject, expired server session and stale invite fail. After sign-out, member removal or session expiry, reject new and unreleased effects; after a fresh verified same-account sign-in, show only current permitted status without replay. A valid guest session alone cannot issue the program owner's grant or inspect the sponsor's payment/PBT detail.
8. Cross the proposed web-session expiry **inside** an already started trial, on separate host and guest session clocks. Reauthenticate each expired actor only as the same verified subject, retain the original trial end/counters and current permitted room state, deny unreleased requests from the old session and reconcile already released native work without replay. Exercise a different subject with the same email and a second client; neither receives the sponsor's trial, grant or PBT view merely from email or possession of a room link. Record the selected host-presence rule separately from session validity.
9. For each sensitive operation, test factor-event ages immediately inside and outside five minutes **at receipt consumption**, receipt ages immediately inside and outside two minutes, a factor event before intent creation, a receipt from an expired initiating session, an old device generation and a wrong purpose/target. A receipt minted when the factor event was fresh must fail if the event ages out before consumption. Do not equate provider token issue time with the verified factor event.

Capture session/grant issuance and expiry instants, account/provider subject reference, installation and recovery generation, grant revision/scope, signed client/service hashes, IPC identity, request/effect key, and expected/actual denial. Redact reusable proofs and private provider/payment data. The linked D02 packet selects the duration, independent TOTP factor-event rule, remote-revoke policy and OS/IPC threat boundary. Independent specification review must accept those selections before D02 feeds the final CFP-1 customer-claim freeze; configured-provider and installed proof remain CFP-2 evidence.
