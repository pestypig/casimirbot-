# CFP-1 personal and hosted capability boundary v1

The [CFP-1 offer](eh-g8-cfp1-product-rights-and-offer-contract-v1.md#selected-offer-free-personal-tools-paid-hosted-collaboration) selects free **supported** single-person MCP tools and subscription-eligible hosted collaboration. This packet replaces the payment and public-policy assumptions in the older [paid-local-Minecraft scope proposal](../evidence/eh-g8-codex-first-paid-product-delivery-v1/cfp-1/scope-claims-policy-proposal.md); that proposal remains a historical technical task and G8-scenario input, not an entitlement specification. The [hosted lifecycle](eh-g8-cfp1-hosted-participant-entitlement-lifecycle-v1.md) owns the operation-specific predicates. This packet names current handler bindings and the missing personal/hosted separation; it does **not** freeze every supported personal tool or declare current public reachability.

### Selected personal routing target before CFP-2 dispatch

The selected base journey has no mandatory room setup for the customer, but current environment MCP handlers require an owner room ID and room feature. The [CFP-1 architecture decision](../evidence/eh-g8-codex-first-paid-product-delivery-v1/cfp-1/2026-09-19-personal-context-architecture-decision-31.md) selects a **service-created, immutable `personal_environment` context** reusing the existing room/source/participant identity chain as the first implementation target. This is an internal compatibility identity with a distinct hosted-room kind, not an ordinary hidden Shared Live Room. Current one-member rooms can issue invitations, so account/room owners must prove these invariants before the target can be accepted:

1. An ordinary verified `user` can create or recover only their own personal context without purchase, invitation or developer promotion. The UI does not require a manual shared-room or task-binding ceremony.
2. Its mode is assigned by the trusted service. It cannot admit a second member, shared source, speaking-floor session or hosted participant operation, and it cannot be converted to a paid room by changing a client field. Hosted creation/join uses a distinct checked transition.
3. Personal connector setup, status, bounded action and stop follow the same owner/source/lease rules through MCP, UI, direct API and immediate effect admission. No paid-hosted predicate appears on these personal operations; no broad `shared_realtime_rooms` flag bypass grants hosted privileges.
4. The personal context's identity and connection consent survive supported reconnect/restart, but effect leases and uncertain actions do not renew or replay. Switching accounts or profiles never adopts the prior owner's context.
5. Select and qualify one ordinary-user full-tool external-client connection profile using the [free personal connection dependency checkpoint](../evidence/eh-g8-codex-first-paid-product-delivery-v1/cfp-1/2026-09-19-free-personal-connection-dependency-17.md). If source credential provisioning, identity or transport has a hosted dependency, identify its cost and failure state before publishing the free-personal claim. A hosted outage cannot be described as an offline personal route unless that route actually passes installed acceptance.

The [Codex local MCP feasibility addendum](../evidence/eh-g8-codex-first-paid-product-delivery-v1/cfp-1/2026-09-19-codex-local-mcp-profile-feasibility-25.md) establishes the same-host HTTP client shape and the packaged service's preferred-port fallback and bearer-custody gap. The later [P1 transport decision](../evidence/eh-g8-codex-first-paid-product-delivery-v1/cfp-1/2026-09-20-cfp1-p1-stdio-priority-decision-163.md) prioritizes a signed local stdio-to-IPC bridge for CFP-2 qualification and holds plain loopback HTTP pending wrong-listener proof. This does not accept an ordinary-user profile, settle the IPC identity or device/offline policy, or establish installed support; the positive and negative P1 fixtures must pass first.
6. Current Minecraft read/action OAuth scope arrays include `helix.rooms.read` alongside environment read/write scopes (`server/mcp/helix-mcp-server.ts`, around lines 528–535). Freeze an operation- and context-specific scope rule: a personal owner context may satisfy the personal lookup without acquiring paid hosted-room read authority, while a hosted room read still requires its own admission and membership. Exercise both positive personal calls and negative cross-room OAuth cases; scope possession alone is never payment or membership evidence.
7. Current non-developer room-source creation allows first-party sessions, not external OAuth (`server/services/shared-live-room-control/service.ts`, around lines 128–142). For the initial personal route, use a narrow first-party wizard source-creation operation and bind the resulting source to only the verified owner context. Do not widen the external OAuth source-manage scope to all personal users or use it as a hosted-source shortcut. Test forged context mode, cross-owner source, and a free personal client attempting shared-room source creation.
8. Create the personal context for the verified owner and trusted installed node/device **before** source creation; the current source-link store mints its source ID only after receiving an existing room ID. Bind that new source to the context with exact owner/node checks and rotate authority on replacement. Project personal connector/tool readiness separately from the shared room's two-member voice readiness, so an otherwise valid personal action is not blocked or labeled `waiting_for_participant`.

This is a selected **target architecture**, not an assertion that the current room model supports a safe personal mode. If room owners cannot make type isolation complete across invite, member, source, media, run, service and effect paths, return to CFP-1 to select a distinct personal binding and update the account/room/connector packets before dispatch. The paid hosted service must be able to fail or expire while a separately authorized personal task and all stop/revoke paths still work.

## Catalog inventory is not the supported-offer register

The source inventory needs a separate support decision. On 2026-09-19, `npm run helix:mcp-evidence:audit` found 128 static registrations and 94 distinct statically named tools across the full Helix MCP and run MCP source files. It exited **1**: 89 of those 94 names lack an evidence-capability descriptor, and nine registration sites use names the scanner cannot resolve statically (the `helix_surface_${operation}` template and eight companion evidence constants). Its eight apparent orphan descriptors correspond to those unresolved companion registrations. These counts are a diagnostic snapshot, not a complete runtime catalog, a public-user allowlist, or a claim that 89 tools are unusable. The scanner also does not classify the coordination-only shadow surface or prove that a registered handler succeeds for an ordinary account.

The [original source-catalog snapshot](../evidence/eh-g8-codex-first-paid-product-delivery-v1/cfp-1/2026-09-19-mcp-source-catalog-11.csv) resolves the finite template to `helix_surface_blank` and `helix_surface_release` and the eight companion constants to their declared names, yielding **104 unique source-level names** at its stated HEAD. The [later drift check](../evidence/eh-g8-codex-first-paid-product-delivery-v1/cfp-1/2026-09-20-cfp1-current-mcp-source-catalog-drift-132.md) adds one environment/Minecraft direct temporal-plan registration, making the [current offer-context worksheet](eh-g8-cfp1-mcp-offer-context-triage-v1.csv) **105 rows**. All 105 remain `unselected` with installed catalog acceptance `not_run`. The current worksheet spans environment/Minecraft (44), room/reasoning/run/local-supervisor (35), client/desktop/evidence/public-UI/surface/visual/workstation (17), and brokerage/realtime-texture (9). Those are name-family counts for triage, not product categories or a count of tools that a particular principal can call. The [offer-context triage](eh-g8-cfp1-mcp-offer-context-triage-v1.md) groups every name into a proposed review lane without selecting or accepting it. Conditional registration, user policy, OAuth, rights and the actual installed `tools/list` result still need separate verification. The personal offer decision must review the non-Minecraft families too; the bounded game pilot cannot silently define the entire free platform.

Before CFP-2.PUBLIC dispatch, the product owner and MCP/account owners must freeze a versioned **supported-offer register** for the selected release artifact. Its decision unit is an advertised **operation in a context**, not the MCP name alone: the same `helix_minecraft_player_action` entry may serve a free owner's personal context and a paid room participant's shared-program context while each evaluates different eligibility and the same underlying effect grant. One row per selected tool/context/capability must identify the exact MCP name and surface, underlying capability ID/version, ordinary-user setup path, account and OAuth admission, owner/room/source/subject binding, consent and effect lease, rights disposition, and positive/negative installed acceptance. Classify each row as `accepted personal`, `accepted hosted`, `shadow/unavailable`, or `experimental/developer`; a source registration starts as unclassified, and a descriptor alone does not promote it. Include every dynamically registered name and compare the actual `tools/list` result for the selected full and coordination-only clients against that register. The public catalog may truthfully show unavailable entries, but customer copy can promise only accepted operations and must explain prerequisites for each one.

The first candidate families are the connection/setup, observation, authority/effect, workflow safety and hosted room operations mapped above. Their exact accepted members remain open because the free personal routing, ordinary-user policy, connector rights and installed journey are not yet qualified. Preserve the full G8 provider-neutral catalog parity obligation in the [claim register](eh-g8-cfp1-claims-evidence-register-v1.md); the first advertised subset is an implementation slice, not a reduction of that release goal.

## Freeze and acceptance handoff

CFP-1.SCOPE/CLAIMS must record an owner-selected register of **every advertised supported personal operation** with its exact MCP name, underlying capability ID, supported version, handler, rights disposition, permission/consent requirements and measured acceptance case. Keep experimental/developer tools outside that advertised set until separately qualified. The table above is a first source-backed slice, not a substitute for that register. CFP-1.POLICY must select the personal-context design and enumerate the affected full MCP, coordination-only shadow, session/API, service enqueue and connector paths. CFP-3.LICENSE must add hosted entitlement only to the selected collaboration operations and preserve the free personal/safety counterexamples.

Minimum paired fixtures: never-subscribed ordinary user completes the selected setup chain (first-party source creation, exact pairing/subject/lease, full MCP observation and approved effect) and each advertised personal operation; expired-trial and expired/refunded hosted users repeat it. A verified trial-active or paid host may sponsor invited authenticated guests within selected limits; a guest needs no separate purchase merely to join but fails without membership, consent or the relevant program grant. Ineligible hosts and guests fail hosted create/join/use, and an eligible sponsor still fails wrong-member, wrong-program, revoked-consent and stale-effect cases. Developer retains the superset under normal native authority; a full MCP handler and a shadow catalog entry are never treated as equivalent. Include OAuth scopes missing/present, personal-versus-hosted room-read separation and source-manage bypass cases. Repeat through UI, direct API, MCP and service calls on the same selected artifact. Rights review must classify the real payment-to-Minecraft effect map, including the internal personal route and trial/paid sponsored rooms, before customer claims or paid release. Existing NAV, ET, PNA, federation and canonical G8 evidence remain independent prerequisites.
