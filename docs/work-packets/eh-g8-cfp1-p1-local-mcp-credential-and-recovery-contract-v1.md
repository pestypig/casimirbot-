# CFP-1 P1 HTTP-helper credential and recovery candidate v1

## Held HTTP qualification branch

For the owner-selected [P1 same-computer product profile](eh-g8-cfp1-free-personal-codex-connection-profile-v1.md), this packet retains a **conditional HTTP alternate**, not the first build route. The [stdio priority decision](../evidence/eh-g8-codex-first-paid-product-delivery-v1/cfp-1/2026-09-20-cfp1-p1-stdio-priority-decision-163.md) and [first qualification contract](eh-g8-cfp1-p1-stdio-local-bridge-qualification-v1.md) now lead CFP-2. Revive HTTP only after account/security and desktop/MCP owners identify a concrete client-supported way to authenticate the loopback server **at send time** and prove the wrong-listener case. If revived, evaluate a signed first-party local `http_headers_helper` for the installed loopback Streamable HTTP `/mcp` entry. It would print one short-lived `Authorization` header as Codex expects; no credential would appear in the URL, static config, environment variable, command argument, log or ordinary UI. It must not expose or forward the native desktop session secret. The user supplies their own Codex account; the separate grant belongs to their verified CasimirBot account and enrolled installation. This packet is **not** an implemented helper or accepted HTTP transport. The [source gap](../evidence/eh-g8-codex-first-paid-product-delivery-v1/cfp-1/2026-09-20-cfp1-p1-mcp-credential-source-gap-136.md) identifies the present missing boundaries.

[Official OpenAI MCP documentation](https://learn.chatgpt.com/docs/extend/mcp?surface=cli) says the helper applies to locally connected HTTP MCP, caches headers, refreshes once after a same-origin 401/403 only if values change, and gives explicit bearer and stored OAuth credentials precedence over helper `Authorization`. The setup wizard must therefore create/inspect one distinct P1 server entry, reject or clear conflicting credential sources **for that entry only**, and confirm the effective request really used the helper. It must preserve unrelated Codex configuration. A wrong-scope 403 is a fresh-approval issue, not a token-refresh loop. The [installed-client transport feasibility check](../evidence/eh-g8-codex-first-paid-product-delivery-v1/cfp-1/2026-09-20-cfp1-p1-client-transport-feasibility-159.md) confirms that the documented helper is a credential source, not a per-request listener-authentication mechanism. If the selected Codex build or installed environment does not honor this behavior, CFP-2 returns to CFP-1 for an explicit alternate client route; no silent native-secret fallback or manual token paste qualifies.

Store one durable client-grant ID/revision bound to profile, device ID, current recovery generation and named client profile. Record approval, scope set, expiry, revoke state and evidence without storing a raw bearer in the database. Account/security owners must select finite browser-session and long-lived client-grant lifetimes before implementation; a cookie lifetime is not a server-session lifetime. |
| Local custody | Keep the long-lived device/client grant proof only in an OS-protected per-user/per-installation store. Command path/arguments contain no bearer, account session secret or provider credential. The store must enforce its chosen Windows-user boundary. Account/security review must decide whether same-user processes are inside the trusted local boundary and, if not, require enforceable broker caller authentication. Admit only the exact active profile/device-generation/grant/scope attribution after the transport and account checks selected below. | Refresh and return | Codex may cache the helper header. An expired/revoked bearer may produce a typed 401 **only before dispatch or native effect** so Codex can invoke the helper and retry once with a changed value. Missing scope returns a pre-dispatch typed 403 with an approval path; do not rely on the helper to fix it. Once a mutating request may have been admitted, a lost response or later authority change must return/reconcile under its durable **effect** identity and must not be translated into an authentication 401/403 that triggers an unbounded second effect. The current `/mcp` route generates a new `X-Request-Id` when none is supplied, so that trace ID is not a replay key. Freeze a caller-stable operation/idempotency identity, show it survives the actual Codex HTTP authentication retry, and reconcile it at the native action ledger; JSON-RPC request IDs and response headers are not substitutes. The wizard/broker recovers the exact client grant and current endpoint after service/Codex restart without a manual token transfer or task rebinding; if the endpoint changes, it updates only the owned server entry and gives the supported reconnect/restart step. | Revoke, loss and account switch | Committed client-grant/device revocation denies **the next request** even while a bearer remains within its five-minute expiry. In-flight work checks the changed generation/revision before effect release; native stop remains separately measured. Every same-ID reactivation route must advance device recovery generation or fail closed to explicit recovery; the current `registerDevice` bypass must close. On profile switch, do not reuse the former profile's helper grant, tool projection, personal context or history. Other enrolled devices remain separate. |
| Outage | If account, grant or device status cannot be verified, deny new issuance and effects with a typed recovery reason. The selected offer makes no general offline-effect promise. Maintain independently valid local stop/revoke where supported, with truthful `verified` versus `pending` native outcome. Meter free-personal credential issuance and verification load in the hosted unit-economics baseline. |

The named client grant is authorization to **connect**, not a program-owner effect grant. Subscription eligibility applies only to separately selected hosted operations. A room host, invited guest and program owner still require their own identities, membership, consent and action grants. No payment or trial can promote the P1 credential into another person's source or player.

### Transport and process trust decision before P1 admission

The helper runs before Codex sends HTTP, while Codex may continue sending a **cached** bearer without re-running it. A hostile listener that takes over the configured loopback port after issuance can receive that header. A service-instance audience on a bearer does not stop the hostile listener from forwarding the captured value to the real service. Therefore a helper-time heartbeat, signed EXE path, loopback address or short TTL alone does **not** meet the wrong-listener requirement.

Before accepting the HTTP-helper profile, the account/security and desktop/MCP owners must freeze and demonstrate a supported server-authentication/transport method that protects the bearer **at send time**, including port takeover after header caching and service restart. If that cannot be proven on the selected Codex build, qualify a separately reviewed signed **stdio MCP proxy over authenticated local IPC** or another concrete client profile; the proxy must still preserve ordinary MCP tools, the free personal journey and independent effect grants. A theoretical fallback is not installed acceptance. The owners must also document whether another process running as the same Windows user is trusted; if it is not, the credential broker needs enforceable caller authentication. Source/client attribution fields alone cannot satisfy that decision. Keep P1 and D02 open until the chosen threat boundary and transport pass their negative fixtures.

| Case | Expected admission or recovery result |
| --- | --- |
| P1C-01 clean ordinary owner | After verified sign-in and enrollment, helper supplies a fresh scoped header; full installed `tools/list` and each selected personal operation work under their independent source/effect grants without checkout or developer role. |
| P1C-02 never-subscribed and expired host | Same personal catalog, setup, action and stop remain available; no hosted create/invite/effect appears from the personal grant. |
| P1C-03 wrong account, OS user or second device | Former profile/device credential cannot be read or accepted; separately enrolled second device receives its own grant and cannot multiply hosted trial/paid limits. |
| P1C-04 revoke and same-ID recovery | Revoke during a cached valid bearer; next MCP request and pre-effect check deny. Re-register a revoked same-ID device and prove old grant/generation stays fenced. Explicit recovery requires fresh approval and new grant. |
| P1C-05 helper/config conflict | Static bearer, stored OAuth credential or missing helper for the owned server entry is detected; do not claim P1 ready or fall back to native desktop headers. Preserve other MCP entries. |
| P1C-06 expiry, scopes and port takeover | Expired token causes one changed-header **pre-dispatch** 401 recovery; missing scope gives a pre-dispatch typed 403 and explicit approval path. Preferred-port collision/restart updates only the owned entry. After a bearer is cached, replace the loopback listener or stale URL and verify that the chosen transport prevents disclosure/replay to a wrong listener. If HTTP helper cannot pass, return to the reviewed alternate transport; do not mark P1 ready. |
| P1C-07 outage, restart and uncertain effect | Separate domain/database, local service and Codex restart cases. Reconnect preserves valid identity but cannot refresh an effect lease or double-execute a request whose result was lost. Stop/revoke and pending outcome are reported precisely. |
| P1C-08 client and audience isolation | A token for another service instance, resource, client grant, profile or recovery generation fails; a remote/cloud MCP execution attempt cannot use the local-helper profile. Direct API, MCP and service calls cannot bypass current authority. |
| P1C-09 automatic authentication retry | Expire or revoke the bearer during a mutating call, lose or alter its response, and trigger the Codex 401/403 refresh path. Authentication rejection before dispatch has **zero** native effect. If admission or an effect may have occurred, a caller-stable effect/idempotency identity and durable native-result reconciliation return the existing or pending outcome; a generated `X-Request-Id`, JSON-RPC request ID, header refresh or repeated POST cannot authorize a second effect. Include revoked authority between enqueue and native release. Record whether the installed Codex retry preserves the operation arguments, including the caller-stable key. |
