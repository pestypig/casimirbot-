# CFP-1 first-party guest-action API contract v1

The [conditional D03 technical freeze](eh-g8-cfp1-conditional-minecraft-shared-action-freeze-v1.md) selects this packet's `v1` schema family for the first Minecraft branch and fixes its invitation, share-confirmation, target-freshness, offer/grant, idempotency and native-action clocks. This API remains unimplemented and commercially conditional.

## Why this route is separate

The selected first hosted trial and subscription each need one invited guest, who may have **no GPT/Codex account**, to request an exact effect on the owner's connected program. The [guest ingress packet](eh-g8-cfp1-hosted-guest-request-ingress-v1.md) selects an authenticated domain-browser baseline. Today's `/api/agi/realtime/rooms` invite/join belongs to the experimental one-model GPT Live room, while the [current action broker](../evidence/eh-g8-codex-first-paid-product-delivery-v1/cfp-1/2026-09-20-cfp1-shared-action-current-source-recheck-229.md) requires the requester to be the paired participant. Neither is a paid/trial guest-action API. The first cohort needs a distinct non-model hosted room and a delegated-action admission branch; a route name by itself creates no authority.

**Proposed D12 browser API namespace:** `/api/agi/hosted/v1/rooms/:roomId`. The host and guest use a new authenticated domain page at `/hosted/rooms/:roomId/actions`. The exact hostname, domain route deployment and page link remain deployment inputs, but this path and the `helix.hosted_guest_action.*.v1` shapes below are the CFP-3 implementation proposal. They do not expose the existing connector ingress, MCP action request schema, raw native player ID, source credential or host model session. The first-party path and optional separately qualified guest MCP path must converge at the **same** server-owned one-use grant, broker admission and native effect ledger.

## First-cohort room and program path

The initial first customer action topology is **one eligible sponsoring host who also owns the one connected program and paired player, plus one invited verified guest on a second client device**. The guest needs no model account or installed connector. A guest-owned program, second installed node, arbitrary member-owned program contribution and an existing-Codex-task binding are outside this initial action claim; they retain their separate G8/federation qualifications. An explicit sponsor handoff may retain the same room, but it **suspends this action path immediately**. If the original program owner remains or later rejoins as a verified member, effect reactivation under a different sponsor requires their independent signed-local share reconfirmation and a fresh exact grant, plus separately accepted sponsor≠program-owner D03/D07/D11/D12 and CFP-3/4 cases. Otherwise no new effect is available; customer notice and a reviewed remedy are required. A future broader claim must add explicit rows and rights/cost/installed tests. The current experimental one-model room's `room.create`, invite, join and source handlers are **not** the first-party hosted room implementation or a shortcut to its acceptance.

For CFP-3 dispatch, use this proposed `helix.hosted_room.*.v1` first-party lifecycle alongside the action routes below. It is a **technical route selection for the first cohort**, not a deployed API or final D12 customer claim. Browser mutations use a current verified CasimirBot session, same-origin/session-bound CSRF proof and a required `Idempotency-Key`; the local confirmation instead uses the separately approved installed-device proof and its own idempotency key, never the browser cookie or CSRF token. The server derives sponsor, member and program authority from protected records.

The server creates the owner-granted offer from the selected owner program binding and a **fresh, bounded** target observation. For the conditional Minecraft H04, one offer means one approved reachable `minecraft:stone` target, `mine` count one and no autonomous approach. For the proposed canvas fallback, one offer means one blue marker at the owner's pre-approved coordinate and document revision. The offer is a presentation reference to a server-held **one-use grant**, never a bearer credential or native effect. An observation becoming stale, target changing, source disconnecting or connector epoch changing invalidates it. D12 must bind the final action/connector/offer and grant expiry and native postcondition; these two examples are not simultaneous customer promises.

## Identity, admission and idempotency

Every **browser** route resolves an active, server-expiring Google/Auth0-linked CasimirBot web session. The separate program-share confirmation authenticates the signed installed device and binds its current owner/source/subject/connector proof to the verified program owner, room and pending share under D02; it never uses the browser cookie as device authority. Creating/revoking offers and creating requests also requires **current** account/room membership and program visibility; the narrow historical-result read instead checks the immutable request actor/sponsor identities and reviewed retention policy, without granting live room/program access. A temporary room `guest`, invite code, matching email, stale cookie, payment receipt or caller-provided profile ID cannot authenticate the actor. Browser mutations require a checked same-origin/session-bound CSRF proof in addition to the cookie. The service derives current room, sponsor term/revision, program owner, node/source/subject, participant and connector epoch from protected records, never from the request body. Creating or revoking the pre-grant requires the program owner's live, independently granted program authority; sponsorship, invitation and media consent are insufficient. The native release path rechecks the consumed grant's recorded owner/requester/subject/target/connector binding, expiry and revocation revision, plus current room, sponsor, member, program and connector authority, even if the HTTP request was accepted earlier; consumption is not a requirement that an unused grant still exist at release. Grant creation via the domain must not pass the owner's local connector credential to the browser.

The client generates one unpredictable idempotency key per deliberate **offer creation, offer revocation or guest request** and keeps it for uncertain HTTP retries. The server looks up `(actor, room, method, Idempotency-Key)`, stores the canonical body hash, and compares that hash on reuse. Same key and body return the same durable offer/revocation/request; same key with a different body is a typed conflict. A concurrent guest double-click, repeated owner grant creation, first-party/MCP race or restart must create **at most one native effect** for one owner grant. A failed HTTP response is not proof that nothing happened; status reads reconcile a durably accepted original request, while a pre-creation denial has no request ID to poll. Reauthentication may inspect current permitted status but never resubmits a request or renews an expired grant. Distinct new deliberate requests require fresh offer and grant admission.

Creating the request may reserve its bounded hosted service work from sponsor PBT; admitting the effect reserves its separate worst-case resource work before enqueue. A denied, duplicate or uncertain request still consumes actual platform work but never counts as a **verified successful trial effect**. Count one effect only from accepted native postcondition evidence; hold an uncertain native result until accepted no-effect or effect proof. Expiry, cancellation, deletion, handoff and sponsor-budget exhaustion fence **new** admissions without erasing a completed owner document/game effect or disabling independent owner stop/revoke. An already released effect follows its separately measured stop and reconciliation contract.

## Result states and customer wording

The page must visibly distinguish an unused `ready` owner-granted offer from a guest request's `admitted_pending_native`, `admission_denied`, `running`, `succeeded`, `failed`, `outcome_unknown`, `canceled` and `expired` states. The first two request states do not imply a connector start or verified effect; `succeeded` requires a native postcondition for the exact target, connector epoch and effect ID. `outcome_unknown` is never shown or billed as a verified success and cannot issue a replacement effect under the same grant. A typed reason may say that membership, term, grant, capacity, source or target is stale without revealing another person's IDs or billing details. Owner stop/revoke and status inspection remain available under the applicable safety/access policy after hosted capacity ends. Result projections are nonterminal observations for an optional MCP reasoning client, not assistant answers.

## Frozen tests needed before dispatch

CFP-1/D12 must freeze the planned method/path/schema and positive/denial fixtures, plus the final action/version, offer/request/grant lifetimes, D07 numerical capacities and D11 rights/customer wording. CFP-3 implements the room, page/API, delegated grant and single broker path; CFP-4 proves them on two physical client devices with separate verified accounts and no guest model account. Required cases:

1. Program owner explicitly creates one exact one-use grant before the guest request. Guest sees only that owner's eligible action offer, requests it once, and one exact native postcondition is visible with correct attribution to both authorized people. An offer, request receipt or UI toast alone fails this case.
2. No effect from invite, payment, room/media consent or offer visibility alone. Wrong account, removed member, non-owner grant creation, different owner/source/subject/target, stale offer or connector epoch, expired browser session and missing CSRF deny before admission and again at the effect boundary.
3. Same-key retries, changed-body reuse, concurrent guest requests on one pre-grant, first-party/MCP race, disconnect/reconnect and handoff cause at most one native effect and one successful-effect count. A lost response returns the original status; an uncertain native outcome holds capacity until reconciled.
4. Expired or exhausted trial/paid term, revoked grant, owner stop, owner sign-out/deletion and room suspension deny new work while preserving status, independent safety controls and the owner's completed native content.
5. The non-model hosted baseline records zero CasimirBot-funded provider calls. A separately selected guest MCP claim needs its own supported client/profile, exact catalog and tool-result re-entry proof; it cannot substitute for this browser case.

**Decision boundary:** this packet chooses a concrete implementation *proposal* for the first-party handoff. It does not freeze the final customer claim or admit the current room/action code. D03/D07/D11/D12 still must agree on one useful rights-cleared action, all numeric limits and the exact approved copy before CFP-1 can close.
