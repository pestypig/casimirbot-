## Exact effect and clocks

One offer authorizes one exposed, loaded `minecraft:stone` at one server-held exact block coordinate, already within the paired player's native interaction range **and focusable without locomotion**. The derived native request fixes `count=1`, `block_id=minecraft:stone`, the approved `target_position` and `search_radius=3`. Search radius is a validation bound, not permission to substitute a neighboring block. No approach, reposition, walk, jump, sprint, navigation, crafting, placement, command, teleport or inventory grant is permitted. Camera orientation may occur only within the approved interaction. A suitable existing tool and inventory space are prerequisites, not harness-created effects.

The current `NativeFabricWorkflowEngine` behind player mod `0.4.12` / adapter `0.4.11` calls `navigateToward` when outside interaction range and may perform bounded repositioning when an in-range target is not focusable. Those bytes **cannot pass this stationary fixture**. CFP-3 must add fail-closed stationary admission and native enforcement: if the exact target is not already in range and focusable, return a typed `stationary_target_not_ready` result before asserting locomotion. The successor path must not call approach/reposition helpers or assert forward/back/strafe/jump/sprint controls. Releasing camera orientation does not permit a position change. This semantic change requires the planned successor manifest/adapter identity above and a rebuilt/re-versioned player artifact; it cannot be shipped under the inspected versions.

An action request consumes the one-use grant atomically even when later broker admission or native work fails; retry with the same idempotency identity returns the same durable status and cannot release again. A genuinely new attempt requires a fresh owner observation, offer and grant. Expiry, source disconnect, target change, connector-epoch change, membership loss, sponsor ineligibility, owner revoke or resource denial fences an unreleased request. An already released effect is reconciled under its finite action identity; it is never replayed from a browser retry.

## Native success, attribution and denial

Success requires all of the following under one immutable effect identity: current sponsor/room/member/program-share state at release; consumed grant identity matching the requester and owner; actual connector identity matching the planned successor manifest; pre-state showing the approved coordinate as `minecraft:stone`, already in range and focusable; native receipt/effect ID; fresh post-state showing that exact approved block removed; no asserted locomotion control or call to an approach/reposition helper; actor block position unchanged and measured position delta no more than `0.01` block absent a separately observed external impulse; and no other block or movement effect attributable to the request. Any external position change cancels attribution and requires fresh evidence rather than being normalized away. Both permitted participants receive a role-filtered result that attributes requester, program owner, target label, request/effect identity and verified outcome without exposing connector credentials or unrelated program history.

If another actor or event changes/removes the target, report `changed_before_effect` or externally satisfied evidence and do not credit a successful CasimirBot effect. An admitted receipt, UI toast, catalog row, inventory change or bare air block cannot establish attribution. Failed, denied, duplicate and `outcome_unknown` results do not consume the verified-success count, although actual hosted resource work remains accounted separately. Uncertainty holds the effect reservation and never grants a replacement under the consumed offer.

Freeze the positive and denial matrix from FH-02/03/04 and FC-05/06: correct two-account no-model guest success with zero locomotion; out-of-range or not-focusable target returns `stationary_target_not_ready` without approach/reposition; no invite/payment/media-consent authority; wrong or stale owner, requester, sponsor, member, room, source, subject, coordinate, block, capability, manifest, connector epoch, CSRF/session, share confirmation, offer revision or idempotency body; concurrent two-use race; source disconnect; revocation before and during work; trial/paid expiry; PBT/resource exhaustion; room suspension; restart; handoff; and direct API/MCP/service bypass. Each denial requires zero unauthorized native effects and locomotion, truthful typed status and preserved owner stop/revoke. CFP-3 implements these fixtures; CFP-4 repeats them on the same signed cohort.
