## Material commercial-rights dependency

The [Minecraft EULA](https://www.minecraft.net/en-us/eula), under Using mods,
includes tools/plugins in its mod definition and restricts monetization. The
[Usage Guidelines](https://www.minecraft.net/en-us/usage-guidelines), under
Extended functionality and modifications, also restrict direct or indirect
checks of out-of-game product access affecting in-game functions. The proposed
software-entitlement-to-Minecraft-action relationship therefore needs explicit
classification and permission review. Making the connector free does not by
itself settle this issue.

The rights reviewer must evaluate the exact package, capability/paywall map,
download flow, intended customer terms and marketing, and document the applicable
permission basis or written permission where required. The selected Minecraft
technical pilot can remain a development reference while this is resolved;
CFP-1 cannot freeze its paid offer or admit dependent commercial implementation
on an assumption. Existing separately authorized environment work continues
under its own packet. No external contact or EULA acceptance is delegated here.

The owner reaffirmed that navigation evaluation mods will be removed before
release. Preserve that exclusion, including the existing Baritone non-shipping
contract, and verify the final installer plus separately provisioned game
profile. This is distinct from the first-party Fabric connector's commercial
classification. Removing evaluation mods is not recorded as permission for
paid access to the remaining connector. No existing user game profile is
modified during this specification stage.

## CFP-1.SCOPE — choose a useful bounded paid task

Owner-selected technical pilot direction: **assisted local Minecraft work through the
user's existing Codex app** on one Windows computer, with a selected player and
work area. The useful journey is inspection -> an evidence-backed proposed
small change -> explicit approval -> a bounded reachable Player Embodiment
operation -> measured world/inventory result -> truthful report and stop/revoke.
The operator can interrupt or change conditions; the agent must re-observe and
replan or cancel. No server-admin action substitutes for player work.

The broad direction is selected; the exact task remains a proposal, not an
accepted product, approved commercial use or proven purchase value.
CFP-0 found only narrow developer/unpacked action evidence. CFP-1 must choose
the exact real user task and capability IDs, not market a short movement test.
Avoid promising autonomous exploration, fluent survival, combat, Nether entry,
companion gathering, or closed-task wake on that evidence.

| Owner choice | Tradeoff and required evidence |

| A — bounded local assistance (recommended initial candidate) | Smaller acceptance surface and no mandatory model resale; prove a useful reachable task, current observations, exact task identity, public-user access, recovery and outcome. | B — durable resource-gathering workflow | Potentially stronger value, with consecutive actions, goal recovery and possibly navigation; requires the corresponding ET6/NAV/perception/monitor/Nether dependencies rather than a scripted demonstration. |

## CFP-1.ENTITLEMENTS — decide what users purchase

### Proposed install and connection experience

1. Install the signed CasimirBot host and inspect compatibility. A download is
   separate from software activation, client authorization and action consent.
2. Choose **Use my existing Codex client**. Detect a supported profile or show
   its official installation/sign-in guidance; do not silently download a second
   Codex runtime. An unavailable client is a truthful setup state, not ready.
3. Sign in to the CasimirBot profile and review the selected software/service
   terms. Trial/purchase is separate from connecting the reasoning application.
4. Connect the client with the exact explained capabilities through the native
   profile flow. Its existing provider account pays for reasoning. CasimirBot
   does not ask for its password/session, a second API key or inference purchase.
5. Detect the existing licensed game installation; disclose the exact companion
   components/download origins, obtain setup consent, select the world/player
   and establish opaque native pairing. Detection is not installation consent.
6. Verify actual catalog, observation and identity readiness. Mutation requires
   a separate bounded approval. Show progress, measured results, interruption,
   revoke and stop in the same public lifecycle.
7. The initial wizard offers no credit purchase or managed model/API enrollment.
   Missing-client, quota and network failures show the relevant connection state;
   they never enable a paid model fallback. Future provider services require a
   separately approved offer and acceptance contract.

This is the proposed base wizard contract, subject to the rights-reviewed
offering. Essential hosted identity/tunnel dependencies must be disclosed even
for same-computer work. No offline reasoning, free forever hosting, provider
chat control or exact-task continuation is promised without its acceptance.

## CFP-2 evaluation boundary before CFP-3 commerce

CFP-1 must freeze a server-owned software-eligibility interface before CFP-2.
Its result binds profile, node, exact capability set, policy revision, finite
validity and provenance (`pre_release_evaluation` or `verified_commercial`),
or returns a typed denial. It grants no account-role change, client access,
environment consent or effect lease. This is a proposed interface, not existing
runtime behavior; any Minecraft relationship remains subject to rights review.

After CFP-1 closure, CFP-2 may prove ordinary-user reachability in an isolated
noncommercial diagnostic installation using a server-owned evaluation adapter
bound to the exact approved test-run manifest. The manifest fixes grant issuer,
profile/node/capabilities/expiry and package identity. Customer requests cannot
mint grants or select the adapter, and normal distribution fails closed without
its approved grant provider. The release guard must reject an enabled evaluation
fixture in a commercial artifact. No developer account, manual token relay or
repository launcher substitutes for the ordinary-user installation path.

This prevents CFP-2 from depending on the commercial engine built in CFP-3.
It does not prove a purchase, offline licensing, renewal/refund or paid product.
CFP-3 binds the authoritative commercial adapter and repeats the positive useful
task and all API/MCP/service denial cases. CFP-4 repeats the full matrix on the
same signed commercial artifact. A fixture result never accepts that later
artifact or relaxes an existing signed-install prerequisite.

Manifest sequencing follows the [bounded acceptance contract](eh-g8-cfp1-bounded-assistance-acceptance-v1.md):
freeze specification and source inputs before dispatch; capture new output
hashes after building and freeze them before evaluation. Child references to
exact artifacts do not require future build outputs to exist before dispatch.
