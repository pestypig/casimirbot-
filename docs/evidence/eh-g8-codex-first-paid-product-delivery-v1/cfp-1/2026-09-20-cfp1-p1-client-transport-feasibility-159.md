| Question | Observed evidence | Contract consequence |
| --- | --- | --- |
| Can the selected local Codex client launch either transport? | Local `codex --version` returned `codex-cli 0.149.0`; `codex mcp add --help` offers `--url` for Streamable HTTP or a command for stdio. [OpenAI MCP documentation](https://learn.chatgpt.com/docs/extend/mcp?surface=cli) says the desktop app and CLI share MCP configuration on the same host and describes both transports. | A signed stdio proxy is a **documented candidate fallback**, not an installed working proxy. The exact desktop client build and executable still require CFP-2 evidence. |
| Is `http_headers_helper` enough to authenticate the HTTP listener? | The [official MCP client contract](https://learn.chatgpt.com/docs/extend/mcp?surface=cli) says helper output is cached for the connection; a same-origin POST `401`/`403` refreshes it once only when output changes. The [configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference) lists helper and HTTP credential fields, but the reviewed fields do not establish listener identity at each send. `apps/desktop/src/loopback-origin.ts` explicitly persists only an address preference; a port probe closes its reservation before the service later binds. | A short-lived bearer from a signed helper plus plain loopback HTTP **fails the specified wrong-listener acceptance case as designed**: a substituted listener may receive the cached bearer. A helper-time readiness probe, service-instance audience, preferred port, Codex server-entry label or URL identity allow-list does not itself prevent that disclosure. Keep HTTP conditional on a concrete server-authenticated transport proven at send time; otherwise qualify the signed stdio/authenticated-local-IPC option under the same personal journey. This is a design inference and threat case, not an observed port-takeover exploit. |
| Does the present `/mcp` route prove retry-safe personal effects? | `server/index.ts` mounts the full HTTP `/mcp`. `server/routes/helix-mcp.ts` selects existing native desktop delegation when native headers are present and has no ordinary-user P1 grant route. If no `X-Request-Id` is supplied, it generates `mcp_req_<random UUID>` for tracing. `server/mcp/helix-mcp-server.ts` separately requires `idempotency_key` for many mutating tools and states that JSON-RPC IDs are not substitutes. | The trace ID is **not** a caller-stable effect key. CFP-2 must prove the selected operation's stable key survives actual Codex 401/403 retry and uncertain-response replay and reaches the durable native-effect ledger. A pre-dispatch auth rejection may be retried; a post-admission uncertain effect must reconcile without a second effect or misleading 401/403 refresh. Existing tool-level keys are useful source machinery, not a blanket guarantee for every selected personal operation. |

**Decision:** retain P1 as the first free personal qualification target, but do not treat plain HTTP plus `http_headers_helper` as an accepted P1 transport. The account/security and desktop/MCP owners must select a send-time authenticated HTTP design and demonstrate cached-header port-takeover denial on the exact installed client, or explicitly qualify the signed stdio proxy with authenticated IPC and an equal ordinary-user tool/effect/recovery matrix. The former is not proven by current docs or code; the latter is not implemented. The [credential contract](../../../work-packets/eh-g8-cfp1-p1-local-mcp-credential-and-recovery-contract-v1.md) retains P1C-01–09 and now distinguishes trace IDs from effect identities. This check does not close D02 or promote CFP-1.
