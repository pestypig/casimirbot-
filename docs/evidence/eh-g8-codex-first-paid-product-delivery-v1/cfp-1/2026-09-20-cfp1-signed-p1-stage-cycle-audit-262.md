# CFP-1 signed P1 stage-cycle audit — 2026-09-20

Program gate: **G8 — Environment-harness release evaluation**. CFP-1 remains active (`specified`); CFP-2/3 remain blocked. This is a stage-dependency audit of current packets, not permission to sign, publish or dispatch a child task.

The [canonical work program](../../../helix-environment-harness-work-program-v1.md) gates CFP-3 on CFP-2 closure and assigns the signed distributable artifact to CFP-3. The [parent CFP stage plan](../../../work-packets/eh-g8-codex-first-paid-product-delivery-v1.md) permits diagnostic CFP-2 work but explicitly says an unpacked diagnostic cannot satisfy a signed-install prerequisite. The [P1 stdio contract](../../../work-packets/eh-g8-cfp1-p1-stdio-local-bridge-qualification-v1.md) and [CFP-2.ONBOARD](../../../work-packets/eh-g8-cfp2-external-client-onboarding-v1.md) require P1S-01–07 on the signed EXE command mode before CFP-2 closure. [CFP-3.SIGNING](../../../work-packets/eh-g8-cfp3-signing-provenance-v1.md) in turn requires CFP-2 completion before admission. Taken literally, these requirements form a cycle: CFP-2 cannot close without a signed cohort, and CFP-3 cannot create the first signed cohort until CFP-2 closes.

**Correction for specification review:** after CFP-1 closes and CFP-2 is admitted, a bounded `CFP-2.SIGNED-QUALIFICATION` child produces a privately held, publicly trusted **signed evaluation tuple** for CFP-2's ordinary-user P1/PNA2 tests. It uses the CFP-1 reviewed planned component/notice boundary, exact source and dependency closure, verified publisher/signature and an independent artifact review. It does not require a public tag, release feed or paid offer and cannot be called the customer release. An unpacked or self-signed developer build remains diagnostic only. CFP-2.ONBOARD/PUBLIC/CAPABILITY consume the exact qualified tuple and may close only after their required positive/denial and interruption/recovery evidence. CFP-3.SIGNING remains after CFP-2 and creates the separate immutable **commercial/customer** signed cohort, with final release-byte/notice/rights checks and distribution coordination. CFP-4 repeats the full useful-task and lifecycle matrix on that same final signed cohort; changes between the evaluation and release tuples invalidate affected evidence rather than inheriting it.

The existing `apps/desktop/scripts/release-preflight.mjs` requires a clean tagged checkout, matching `GITHUB_SHA` and release tag; `.github/workflows/desktop-release.yml` triggers on `desktop-v*` tags and uses the production release environment. The evaluation lane must not call that path an untagged release success or weaken its checks. At implementation dispatch, choose a separate private no-publication signing recipe with its own source/build/provenance verification and single operator, or stop if such a recipe and signing identity are unavailable. The [individual signer screen](2026-09-20-cfp1-individual-code-signing-route-screen-260.md) is a conditional feasibility input, not an enrolled signing account. The exact privately signed tuple is CFP-2 output evidence, not a CFP-1 closure prerequisite.
