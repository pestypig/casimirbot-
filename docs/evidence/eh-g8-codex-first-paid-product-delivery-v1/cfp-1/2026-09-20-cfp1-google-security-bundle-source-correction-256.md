# CFP-1 D02 Google Security Bundle source correction — 2026-09-20

Program gate: **G8 — Environment-harness release evaluation**. CFP-1 remains active (`specified`); CFP-2/3 remain blocked. This is a primary-provider-documentation correction to [source audit 183](2026-09-20-cfp1-google-fresh-proof-source-audit-183.md), not a configured-client test or account/security acceptance. No provider, session, account or runtime setting changed.

| Current official source | Finding and bounded consequence |
| --- | --- |
| [Google Security Bundle](https://developers.google.com/identity/siwg/security-bundle), checked 2026-09-20 | A published, verified app with **Session age claims** enabled can request signed `auth_time` using GIS Web `essential_claims: "auth_time"` or OIDC `claims`. The feature is disabled by default. `auth_time` is the last Google Account authentication on the current browser/device, distinct from the ID token's issuance time. The current CasimirBot GIS client does not request or validate this claim; no verified-app/Security-Bundle configuration was tested. |
| [Google Security Bundle](https://developers.google.com/identity/siwg/security-bundle) and [GIS JavaScript reference](https://developers.google.com/identity/gsi/web/reference/js-reference), checked 2026-09-20 | Google explicitly states that it does **not support Google Account reauthentication requests**. GIS may return a credential through `auto_select` without interaction. Asking for `auth_time`, showing an account picker or obtaining a new token cannot force a stale Google session to become fresh. A separate authorization-code flow is **not required merely to request** the claim and is not a documented solution to stale SSO. |
| [Auth0 reauthentication limits](https://auth0.com/docs/authenticate/login/max-age-reauthentication), checked 2026-09-20 | An upstream social/federated exchange can update Auth0 `auth_time` even if the user did not authenticate again at Google. Auth0 cannot enforce upstream reauthentication. Treat an Auth0-hosted MFA or first-party/passkey challenge as a **different** proposed step-up whose subject linkage, enrollment, recovery and operation-bound proof need review; do not call Auth0 federated `auth_time` fresh Google proof. |

**D02 decision implication:** retain Google for ordinary verified account sign-in, and treat GIS Security Bundle as a candidate *freshness observer*. The selected P1 fresh-proof policy has no documented reliable Google-only completion path for an already-stale Google SSO session. Account/security and product owners must accept a separately reviewed reachable step-up (or explicitly revise the sensitive-operation policy) before the full Google-only installation/recovery journey becomes a customer claim. Test stale-SSO denial and positive equivalent-step-up recovery. This does not close D02, D11 or D12.
