## Selected target and reason

For the first free personal MCP implementation slice, use a **service-created, immutable `personal_environment` context backed by the existing room/source/participant identity chain**, with a distinct hosted-room kind and operation-specific admission. The context is a compatibility identity for one verified owner and their selected installed node/device. It is not a customer-created Shared Live Room, a subscription trial or an invitation-capable room. The service assigns its kind and binds the exact owner and trusted installed node/connector installation; neither a client field, payment, room membership nor a later handoff can change its kind or adopt another owner's context. Source creation follows context creation: the service binds the newly minted source ID to that context after checking owner and node identity. Source replacement rotates source binding and effect authority rather than inheriting leases or pending effects.

This target minimizes duplicate effect-authority paths: `server/db/migrations/039_environment_connector_platform.ts` binds environment connectors to `room_source_binding_id` and `room_id`; `server/services/environment-connectors/actions/authority-store.ts` and `actions/action-broker.ts` join room/source records at authority and effect time. A distinct personal binding would require an additional admission path through probe, subject, lease, credential, action and control data. The choice is conditional on proving complete type isolation; if account/room owners cannot enforce the guards below, return to CFP-1 and select a distinct binding before implementation, rather than weakening the paid/personal boundary.

## Required isolation and failure fixtures

Current `server/services/helix-ask/realtime-room/room-store/rooms.ts` creates a one-member `waiting_for_participant` room using the two-slot shared-room contract. `room-store/invites.ts` can admit a second member, and `actions/action-broker.ts` rejects a closed room but does not use `waiting_for_participant` as a personal safety marker. Therefore an ordinary hidden shared room is **not** the selected design. CFP-2.PUBLIC and room/account owners must freeze a database-backed immutable kind and prove the following at service, route, MCP and native effect boundaries:

1. One authenticated owner can create/recover only their own personal context through a first-party setup path without purchase, invitation, developer promotion or manual shared-room setup. Its stable key includes the owner account and trusted installed node/connector installation or device identity, plus a generation when replacement requires one. The source ID is minted **after** the context exists and bound to it with exact owner/node checks; it is not an input to the context-creation key. A direct client call cannot forge kind, owner, node or source, and a second account cannot list, inspect or adopt it.
2. Every invite issue/redeem, second-member admission, source sharing, room floor/media, run/chat binding, hosted read/management and sponsor handoff rejects a personal context with a typed reason. Personal context cannot be converted to hosted by updating a row, adding a subscription or reusing its opaque ID. Hosted rooms retain their independent entitlement, member/role, consent and program-owner grant predicates.
3. Personal source creation/pairing, observation, approved bounded action, status and owner stop/revoke use a narrow owner-only route. The current base `user` policy locks shared rooms/source ingress; Minecraft MCP handlers also require `helix.rooms.read` and `requireCurrentRoomFeature()`, while local lifecycle launch is developer-gated. CFP-2 must change these admission checks **per personal operation/context** without granting general room/source-manage scope or weakening the existing self-player and native lease checks. A first-party wizard may create the source; an external OAuth actor must not gain general source ingress by possessing a personal client token.
4. Effect admission must recheck context kind, exact owner, source, subject, current lease and revocation at enqueue and connector/native execution. A personal request cannot spend a hosted grant; hosted expiry/refund/outage cannot deny independently valid personal work or direct stop/revoke. Stale action, account switch, device replacement and reconnect never replay effects or restore a revoked grant.
5. The selected ordinary-user full MCP client profile must actually connect to the installed local service, discover the current port and use reviewed credential custody. Test both full and coordination-only `tools/list`; a connected or shadow catalog is not accepted execution. The [local HTTP feasibility checkpoint](2026-09-19-codex-local-mcp-profile-feasibility-25.md) sets same-host Streamable HTTP as the first qualification target, not a proven customer route.
6. Personal connector/tool readiness is projected from the owner's authenticated client, source, subject and current grant. It does not inherit Shared Live Room's two-present-member voice readiness: a one-member room currently reports `waiting_for_participant`, which must neither block an otherwise valid personal action nor be shown as the personal customer's next setup step. Hosted voice readiness remains governed separately.

CFP-2.PUBLIC owns the typed context, account/room policy and bypass tests; CFP-2.ONBOARD owns the no-manual-room setup and reconnect journey; CFP-2.CAPABILITY owns selected program operations and local native postconditions. CFP-3.LICENSE/COMMERCE must put hosted eligibility only on hosted operations and preserve never-subscribed, expired and refunded personal counterexamples. CFP-4 repeats both contexts through UI, MCP, direct API/service and the same declared installed artifact. The [104-name worksheet](../../../work-packets/eh-g8-cfp1-mcp-offer-context-triage-v1.md) remains unselected; this architecture does not choose which operations are advertised or settle Minecraft rights.

**Stage decision:** CFP-1 remains active under G8. This architecture target makes the CFP-2 handoff more specific but does not dispatch CFP-2 or CFP-3. Exact supported operations and client profile, the remaining O-01–07 terms, rights dispositions and independent final contract review remain required before CFP-1 closure.
